# CBL Ban Importer

Copies the bans of the partner ban lists into the CBL database and marks the bans whose expiry has passed as expired, checks once a day that every player's reputation points still match their bans (see [Reputation check](#reputation-check)), then updates the Steam profiles, reputation points and ranks of the players, recalculates the export ban lists and sends their changes to BattleMetrics. One run does all of this and exits. The script that starts the importer runs it every 6 hours, and can run it every hour (see [Running more often](#running-more-often)). With `IMPORTER_MODE=loop`, the same image runs as a service instead, in the Portainer stack, with a cycle every 10 minutes (see [Running as a service](#running-as-a-service)). Of each list's bans, only those that are new or changed are written (see [Importing a ban list](#importing-a-ban-list)), and a BattleMetrics list is read in full about every 30 minutes, at a time of its own, so that the lists' full reads are spread over the runs, or when it needs to be: otherwise only its newest page is read (see [Head polls and full reads](#head-polls-and-full-reads)).

## Running it

The importer runs on Node.js 26, like the other services, as `yarn start-ban-importer` or with the `werewolfboy13/cblimporter` image. The script that starts it runs each run in a container of its own, with `--init`, so a `docker stop` lets the run stop cleanly, and `--stop-timeout 60`, so the run has time to: once it reaches a safe point, it ends within 45 seconds.

```bash
docker run -d --init --stop-timeout 60 --env-file .envimporter --name cblimporter \
  --network=cbl_backend --network=cbl_frontend werewolfboy13/cblimporter:sha-<commit>
docker wait cblimporter # Waits for the run to end, and prints its exit code.
```

Until the container is removed, `docker inspect -f '{{.State.ExitCode}}' cblimporter` gives the run's exit code and `docker logs cblimporter` its output. Before the next start, the script removes it with `docker rm cblimporter` once the run has ended, never with `docker rm -f`, which kills a run that is still going before it can save its record, and throws away its output with its JSON line.

Only one run works at a time. A run holds two MySQL locks while it works (see [The locks](#the-locks)), and a run started meanwhile, or while the importer service runs, is skipped, with exit code 75. With the same container name for every run, though, a start while a run is still going fails in Docker, with exit code 125 as the name is in use, and never reaches the importer. A stuck run is then ended by its time limit, `IMPORTER_MAX_RUN_SECONDS`, or at the latest 60 seconds after it, so keep that shorter than the time between starts. For such a start to be skipped instead, and to check whether the importer is stale (see below), give each run a name of its own, e.g. `--name "cblimporter-$(date +%Y%m%d%H%M)" --label cbl-importer`. `docker ps -a --latest --quiet --filter label=cbl-importer` then finds the latest run, and `docker container prune --force --filter label=cbl-importer` removes the containers of the runs that have ended, never one that is still going.

### Exit codes

| Code | Meaning                                                                                                         | What to do                                                                                                  |
| ---- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `0`  | The run finished.                                                                                               | Nothing.                                                                                                    |
| `1`  | The run failed, e.g. it could not reach the database, a step or migration failed, or it lost its locks.         | Read why in the run's JSON line or the log channel. The next run starts afresh.                             |
| `3`  | The run stopped part-way, as it received `SIGTERM` or `SIGINT`, or took longer than `IMPORTER_MAX_RUN_SECONDS`. | Nothing, unless it keeps happening. The next run picks up the work.                                         |
| `75` | The run was skipped, as the importer service or another run, e.g. one started by hand, holds the locks.         | Nothing. If no run has succeeded for 3 cadences, e.g. as the other run is stuck, it posts that it is stale. |

The importer service exits with codes of its own (see [Running as a service](#running-as-a-service)). An `IMPORTER_MODE` that is neither `once` nor `loop` starts nothing, and exits 1.

### The locks

The importer holds two MySQL locks, on a connection of its own, named after the database it works on:

- **The service lock**, `cbl-importer-service:<database>`, for as long as its process runs: a run for its whole run, and the importer service from when it starts until it stops. Only one importer holds it at a time, so a run started meanwhile is skipped.
- **The run lock**, `cbl-importer:<database>`, while it works on the database: a run for its whole run, and the importer service during each of its cycles, but not between them. The bot checks it before giving a ban list a new type or source, and refuses the change while it is held, so between the service's cycles the change works. Its other commands, export ban list removals among them, do not wait for the importer (see the bot's README). Importers from before the service lock held only the run lock, for their whole run, so the bot still sees their runs, and a cycle of the service that finds the run lock held waits for such a run to end.

A run that finds either lock held is skipped, and its line, its record and any stale alert it posts say which: `The importer service or another run holds the service lock`, which the service holds even between its cycles, when the bot finds the run lock free, or `Another run holds the run lock`, which only a run of an importer from before the service lock holds without the service lock. A service that loses its locks says that it lost its locks, as between cycles it holds only the service lock.

MySQL frees both as soon as their connection closes, e.g. when the importer exits or is killed. The importer uses the connection every minute and, from this version on, has MySQL close it once it has not been used for 5 minutes, rather than after MySQL's usual `wait_timeout` of 8 hours, so an importer cut off from MySQL without closing the connection, e.g. by a network partition, leaves its locks held for at most about 5 minutes. An importer from before the service lock leaves `wait_timeout` as it is, so one that is cut off leaves the run lock held for up to 8 hours, or about 2 hours with TCP keep-alive, and meanwhile the service's cycles wait for it (see [Stops and exit codes](#stops-and-exit-codes)), and the bot refuses the changes it refuses during a run. To see which connections hold the locks, in the CBL database:

```sql
SELECT IS_USED_LOCK(CONCAT('cbl-importer-service:', DATABASE())) AS service, IS_USED_LOCK(CONCAT('cbl-importer:', DATABASE())) AS run;
```

Each is the ID of the connection that holds the lock, or `NULL` while it is free. `SHOW PROCESSLIST;` shows how long each connection has been idle: `Time`, in seconds, while its `Command` is `Sleep`. An importer that is still running uses its locks' connection every minute, so one idle for longer belongs to an importer that is gone. `KILL <ID>;` closes a connection, which frees its locks at once. While the importer service runs, it holds the service lock itself, so kill the run lock's holder only when it is another connection than the service lock's: killing the service's own connection only makes the service exit 1 and start again, and its next cycle still waits.

```bash

docker logs cblimporter 2>&1 | grep -F '{"event":"cbl-importer-run"' | tail -n 1 | jq '{outcome, exitCode, seconds, reason, phase}'
```

The steps that count what they do keep their counts also when they fail or stop part-way. The expiry and Steam steps, and the reputation check, start counting once their first read has worked, so one that fails before, e.g. as the database is unavailable, has no counts, rather than counts that say nothing was due:

| Step                    | Counts                                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `importBans`            | The totals of its summary line, how many of its `lists` it `imported` and, in `banLists`, each list's own counts and errors.                                                                                                                                                                                                                                                                                         |
| `expireBans`            | How many bans whose expiry has passed it found (`due`) and marked `expired`, and how many different `players` it queued for a recalculation.                                                                                                                                                                                                                                                                         |
| `checkReputationPoints` | Whether the reputation check `ran`. When it did, how many players it compared with their bans (`checked`), how many of them had points that did not match their bans (`mismatched`), how many of those it `queued` for a recalculation, at most 1,000 a run, and how many it `left` for later runs. When it did not, why: it is `off`, or not due until `dueAt`, in UTC (see [Reputation check](#reputation-check)). |
| `updateSteamUserInfo`   | How many Steam users were `due` a refresh and, of those, how many were `new` (never refreshed, or queued for a refresh), how many it `updated`, how many Steam did not have (`missing`), how many it `skipped` as their IDs are not SteamIDs, how many profiles it could not save (`unsaved`), how many are `left` for later runs, and how many `calls` it made to Steam.                                            |
| `updateExportBans`      | How many `players` it recalculated.                                                                                                                                                                                                                                                                                                                                                                                  |
| `exportExportBans`      | How many export bans were `queued`, and of those, how many it `created` and `deleted`, and how many `failed`.                                                                                                                                                                                                                                                                                                        |

`importBans` also counts the lists that import one of CBL's own export ban lists (`selfImports`) and those CBL can no longer read on BattleMetrics (`accessLost`), and says how the access check went (`accessCheck`: `ok`, `failed`, `off`, `unused` when no BattleMetrics list was imported, or `running` when the cycle was ended at once while it was still being made, see below), and, once it was started, how long it took, or had taken by then, in seconds (`accessCheckSeconds`), which the first BattleMetrics list waits for, and which is not in that list's `seconds`. Its `held` counts the bans the lists no longer have that were kept for now, of which `pending` wait for a later complete read of their list. A list that was only polled counts the bans it keeps as the run found them at its start, as a poll removes none, so these counts, and the status message's, do not drop to 0 on runs that only poll it. `moves` counts the bans whose player is no longer one of their SteamIDs (see [Importing a ban list](#importing-a-ban-list)). `headPolls` counts the lists of which only the newest bans were read and `fullReads` those read in full, and `requests` the BattleMetrics requests for pages of bans: for lists' newest pages (`head`), for the pages a poll followed after a list's newest page (`follow`), and for the other pages of lists read in full (`full`). A request the BattleMetrics client tried again counts once, and the access check's few requests are not counted (see [Head polls and full reads](#head-polls-and-full-reads)). A dry run's counts say what the import would have done, and it has `"dryRun": true`. A run that left out suspended ban lists counts them (`suspended`), and one that caught up with resuming lists names them (`caughtUp`), and so does each such list's own entry (see [Paused ban lists](#paused-ban-lists)).

Each list in `banLists` says how long its import took in the run, in seconds (`seconds`), both attempts together for a list tried again, so a slow list stands out, how it was read (`read`: `head` or `full`), and for a list read in full, why (`reason`, see [Head polls and full reads](#head-polls-and-full-reads)), with, for drift, BattleMetrics' count and the count expected (`drift`). It has its `state` when it is not `ok` (see [Ban list states](#ban-list-states)), and, when they apply: `pending`, `moves`, `hold` (`empty`, `full` or `large`, for removals that wait for an admin, see [Removing bans](#removing-bans)), `holdEnded` (`full` or `large`, for a hold an earlier run began that the read ended: as enough of its bans came back, also in a read an admin confirmed, as an admin confirmed it, which would otherwise have kept it, with `massRemoval`, or as its source was replaced, with `replace`), `cameBack` (how many of the bans held for an admin the read found again, which are no longer held, whether or not their hold ended), `incomplete` (it was not read in full), `unchanged` (a remote list whose file has not changed), `replace` (its old source's bans are being replaced), `failedToSave`, `attempt`, `gone`, `sourceChanged`, `massRemoval`, and the `error` and the `stage` it failed at, with, for a list that failed on a page of its bans, the page (`page`). A list that fails before what its read changes of a hold is written keeps that hold as it was, though its entry still gives `hold`, `held`, `pending`, `holdEnded` and `cameBack` as the read would have left them, and the run's totals count them; its `state`, `error` and line say it failed. A list tried again also says how its first attempt ended (`firstAttempt`): how long it took (`seconds`, which the list's own include), and its `error`, `stage` and `page`, as for a list that failed, so a page that fails at times shows also when the second attempt read the list, e.g. `jq '.counts.importBans.banLists[] | select(.firstAttempt) | {id, seconds, firstAttempt}'`.

An import that stopped part-way through a list, e.g. as a cycle reached its time limit while BattleMetrics was slow to answer that list's pages, leaves that list out of its totals, `imported` and `banLists`, as its summary line does, and gives it on its own, in `stopped`: its counts, as for a list in `banLists`, how long its import had taken (`seconds`, both attempts together at a second attempt), and where it stopped (`stage`, and `page` for a list stopped on a page of its bans). The importer service can also end a cycle at once, while its import is still under way, 45 seconds after `SIGTERM` or 60 seconds after its time limit (see [Stops and exit codes](#stops-and-exit-codes)): the list it was importing then is given on its own in the same way, in `inProgress`, with how long it had taken by then, and what it was doing (`stage`, e.g. `fetching it`, with the `page` it was reading, `waiting for the access check`, or `saving its bans`), and the access check, if it was still being made, as `running`. So the list that held up an interrupted cycle shows, e.g. `jq '.counts.importBans | .stopped, .inProgress'`, beside the slowest of the others, `jq '.counts.importBans.banLists | sort_by(-.seconds) | .[0:3]'`.

A run that held the run lock also saves its record in the database, in the importer's `ImporterState` table:

| Row                  | What it holds                                                                                                                                                                                                                                                        |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lastRun`            | The latest run's record, as its JSON line shows it.                                                                                                                                                                                                                  |
| `lastSuccessAt`      | When the latest successful run started: one that exited 0 and imported at least one ban list, if any.                                                                                                                                                                |
| `recentRuns`         | The latest 100 runs' records, oldest first, without per-list counts but for a stopped import's `stopped` and `inProgress`.                                                                                                                                           |
| `lastStaleAlertAt`   | When the run, or the skipped start, that last posted that the importer is stale started.                                                                                                                                                                             |
| `lastRunMessage`     | The ID of the latest run's status message in the log channel, and when that run started (see below).                                                                                                                                                                 |
| `steamRefreshCursor` | The ID of the last player due a Steam profile refresh that a run took, after which the next run carries on (see [Steam profiles](#steam-profiles)).                                                                                                                  |
| `reputationCheck`    | When the run that last made the reputation check started (`startedAt`), from which the next run tells whether it is due, when it checked (`checkedAt`), and how many players it `checked` and `queued` (see [Reputation check](#reputation-check)).                  |
| `importerService`    | The importer service's status message, and when its process started and, once it ended as it should, when and how, and the old copies of the message still to be deleted (see [Running as a service](#running-as-a-service)).                                        |
| `lastLogMessage`     | The ID of the newest message in the log channel that CBL's services posted, as each writes it, and which posted it: `web`, `bot` or `importer` (see [The status message at the bottom](#the-status-message-at-the-bottom)). The web server and the bot write it too. |

```sql
SELECT name, updatedAt, value FROM ImporterState;
```

A run that never held the lock, e.g. one that was skipped or could not reach the database, only prints its line, except that a skipped start that posts that the importer is stale saves when it started, in `lastStaleAlertAt`. A run left waiting for something that can never happen, e.g. an answer on a connection that is gone, is ended as failed, and prints and saves its record. One ended at once by a second signal or 60 seconds after its time limit prints its line but has no time to save it. A run that is killed, e.g. by `docker rm -f` or for running out of memory, prints neither, and then only its exit code, and its status message in the log channel, tell how far it got.

### Staleness

The importer is stale when no run has succeeded for 3 times `IMPORTER_CADENCE_SECONDS`, which is 18 hours by default. A run succeeds when it exits 0 and imports at least one ban list, so runs during a BattleMetrics outage, when every list fails, do not count. The importer then posts that it is stale to the log channel, and again every `IMPORTER_CADENCE_SECONDS` while it stays stale. It compares when runs started, so with a run every `IMPORTER_CADENCE_SECONDS`, the alert comes with the 3rd run in a row that does not succeed, however quickly the runs fail, and it allows 5 minutes, or a tenth of the cadence if that is less, for runs that start a little early or late. Set `IMPORTER_CADENCE_SECONDS` to how often the script starts a run, as it also sets how many Steam profiles a run refreshes (see [Steam profiles](#steam-profiles)).

Only the importer checks: at the end of every run that did not succeed, and whenever a start is skipped, as another run holds the lock. So while no run starts at all, nothing is posted. Whichever run or skipped start posts saves when it started, so no other posts again within the cadence.

The importer service checks at the end of every cycle that did not succeed, except one that ends as the service stops, and, while it stands by for the service lock, or a cycle waits for the run lock, once a cadence. Its cadence is `IMPORTER_CYCLE_SECONDS` unless `IMPORTER_CADENCE_SECONDS` is set, so at a cycle every 10 minutes it is stale after 30 minutes without a successful cycle, and posts so again every 10 minutes while it stays stale.

### The log channel

The importer posts to `DISCORD_LOG_WEBHOOK` one status message for each run, and otherwise only what may need looking at: failures, removals held for confirmation, invalid settings, dry runs, staleness and players whose reputation points did not match their bans, each as a message of its own. The import's totals appear in the status message; its summary line (`Got N deleted bans. Imported 20 ban lists: …`) is only printed in the console, with everything else. The importer service posts differently, as `IMPORTER_LOOP_DISCORD` says (see [Running as a service](#running-as-a-service)), and the rest of this section is about runs in once mode.

As soon as a run holds the run lock, it posts its status, an embed, and keeps it up to date while it goes, editing it at most every 15 seconds. The embed shows that the run is in progress, in blurple, when it started, in each viewer's own time, how long it has taken, the commit it runs and any importer migrations it applied. Below them are the run's steps: each finished one with a tick, its time and what it counted, the one under way with how long it has taken and a bar of how far it has got, e.g. `18,250 / 145,155 players` or `7 / 20 ban lists`, and those still to run.

When the run ends, it edits the embed a last time, before it releases the lock, to show how it ended: finished in green, failed in red, lost its locks in red, or stopped in orange, as it received `SIGTERM` or `SIGINT` or took longer than `IMPORTER_MAX_RUN_SECONDS`. The embed then shows how long the run took, each step's time and counts (the import's totals as in its summary line, with how many lists it only polled and read in full and the BattleMetrics requests that took, e.g. `20 ban lists: 2,061 bans fetched, 150 new, 0 updated, 0 removed, 0 held, 0 lists failed; 20 polled, 0 read in full, 21 BattleMetrics requests`, the bans marked expired, the players the reputation check compared with their bans, those it queued and those it left for later runs, when it ran, the Steam profiles updated and those left for later runs, the players recalculated, and the export bans created and deleted), and for a run that did not finish, the phase it ended in and why. A run in which the reputation check was not due, or is off, leaves it out, unless the run stopped right after it, as it then ended in it, which the embed names: the check's line then says why it did not run. A run that is skipped, or fails before it holds the lock, posts no status, only its failure line, if it failed.

Of the import's lines about each list, only those that need looking at are posted: a list that failed, or was not read in full, one whose bans are held for an admin, on every read of all of it while they are, with how many of them came back, and when that hold ends as they came back, which also says when an admin's confirmation removed the rest at once, one that removed a large part of its bans after a confirming read, which any line it posts says, one whose old source's bans are being replaced, which also says which hold that ended, one that lost bans as an admin allowed it, which also says which hold that ended, when it would otherwise have gone on, and one whose bans could not all be saved. A BattleMetrics list that failed on a page of its bans says which, and of about how many, by BattleMetrics' count of its bans, or before its first page, by the count its row kept, but for a list whose source was changed, e.g. `Failed to import ban list (ID: 115) while fetching page 37 of about 93, so none of its bans were removed. ApiError: BattleMetrics GET bans failed after 5 attempts: timed out after 30s`. A list that a stop came in the middle of says where it was, and how long its import had taken, e.g. `Stopped importing ban list (ID: 115) while fetching page 37 of about 93, after 61.2s, as the run is stopping, so none of its bans were removed.` A list whose missing bans wait for a later read, which needs nothing doing, only goes to the console, as do each new, changed or moved ban, each list that was only polled (`Polled ban list (ID: 46): …`), why a poll read a list in full after all, the BattleMetrics requests of the run, after its summary line, and a list that is not read in full again, after it was not in its last run either, as its first one was posted. In a dry run, every line about a list goes to the console.

A run whose last edit does not reach Discord leaves its embed saying it is in progress: one that was killed, ran out of memory, or was ended at once by a second signal or 60 seconds after its time limit, and one that ended as usual while Discord was down or refused the edit. So each run saves which message is its status in `ImporterState` (`lastRunMessage`), and the next run that holds the lock reads that message back and, if it still says it is in progress, corrects it, once, in the background. A run that saved its record is shown as it ended, drawn from its record, with a footer that says so. One that saved none ended without saying how, so it is marked as having ended without finishing, in red, keeping how far it had got.

Nothing the importer does waits for Discord: its messages are sent in the background, one request at a time, and at the end of a run for at most what is left of its 45 seconds. The status goes ahead of the other messages, so it is not dropped when Discord falls behind. Discord has 30 seconds to answer the status's post, and if it rate limits or fails the post, or does not answer it, the status is posted again 15 seconds later, so the run still gets one. If Discord refuses to edit it, e.g. as someone deleted it, or to post it, the run stops trying. Without `DISCORD_LOG_WEBHOOK`, or with one that is not a Discord webhook, nothing is posted.

Two kinds of embed can still say a run is in progress for good, as no later run knows of them: one Discord posted without answering within those 30 seconds, as the importer never learns which message it is and posts the status again, and one whose post Discord answered only once its run was ending, which the run does not save, should its final edit then not reach Discord.

## Ban list states

After each list's import, the importer saves how it went in the list's row of `BanListSyncs`, so the next runs know it too. The row is saved once the run knows how the import ended: right after it, or, for a list the run tries again after the others, or one CBL cannot read, once every list has been tried. A list is in one of these states:

| State         | What it means                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ok`          | Its latest import went as it should.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `failing`     | Its latest import failed, e.g. as its source was down, or it was not read in full. Its bans are kept as they are, but for any new or changed bans a read that was not complete found.                                                                                                                                                                                                                                                                                                                                                                               |
| `held`        | It was imported, but some of the bans it no longer has were kept for now: until a later complete read of it confirms they are gone, or, if it seems to have lost all its bans, until an admin confirms it or one of them comes back, or, if it lost a large part of them at once, until an admin confirms it or so many of them came back that those still missing are no longer a large part of the bans it had then, or has, if fewer (see [Removing bans](#removing-bans)). A poll of its newest bans leaves it `held`, as a poll never checks for removed bans. |
| `access_lost` | CBL cannot read it on BattleMetrics, or BattleMetrics does not list it among the ban lists the CBL organisation can see. It is still fetched, and any new bans it gives are saved, but none of its bans are removed, even with `IMPORTER_ALLOW_MASS_REMOVAL`.                                                                                                                                                                                                                                                                                                       |
| `self_import` | Its source is one of CBL's own export ban lists. It is neither fetched nor swept.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

**Failures.** A list that fails 3 runs in a row is posted about once, at the 3rd, or at once if it starts failing with more, e.g. after a while in which it imported a CBL export ban list. A run that tries a list again after the other lists counts as one run: the list's row waits for the second attempt, so a list that the second attempt imports is neither counted as failed nor posted about. Once the list imports again, it is back to `ok`, and is posted about again only after another 3 failed runs in a row. Each failed run still posts its own line, as before, except when it only shows again that CBL cannot read a list (see below).

**Lost access.** A list is taken to be one CBL can no longer read when:

- the access check, once a run, does not find its source among the ban lists BattleMetrics says the CBL organisation can see (`GET /ban-lists`, every page), comparing IDs ignoring case, hyphens and spaces;
- BattleMetrics answers its fetch with HTTP 404, Unknown ban list; or
- BattleMetrics answers with no bans on the first page but still counts some, as it does for a list CBL may see but not its bans. Such a list has not emptied, so its fetch fails.

A list that loses access is posted about once. A list that BattleMetrics does not list, but whose fetch still works, is posted about as such: its new bans are saved, but none are removed until BattleMetrics lists it again. For any other, the alert says what to do: if its owner has stopped sharing it with the CBL organisation, remove it with `/banlist remove`, which removes its bans too. When at least 3 lists, and at least half of the BattleMetrics lists a run tried, lose access in the same run, they are posted about together instead, as CBL's own BattleMetrics token, or its role in the CBL organisation, is then the likelier cause: check the token before removing any of them. A list whose fetch shows that CBL has lost access to it is not tried again later in the run. Once it has been posted about, a failed fetch that only shows this again goes to the console, while any other failure of it, e.g. during a BattleMetrics outage, is posted as for any list.

The list stays `access_lost` until a run shows that CBL can read it again: its fetch works, while the access check finds it, or is off. A run that cannot tell, as the check could not be made, or the fetch failed for another reason, e.g. during a BattleMetrics outage, leaves it as it was: it is not swept, posted about again or said to be back to normal, and its row keeps why it lost access. Once CBL can read it again, it is checked for removed bans again, and the console says it is back to normal.

A failed read of BattleMetrics' ban lists never holds up the import: that run goes without the check, and says so in the console and in `accessCheck`. As lists that lost access stay so meanwhile, a check that keeps failing keeps them from being swept. `IMPORTER_ACCESS_CHECK=0` turns the check off, after which such a list is back to normal once its fetch works; the other two signs of lost access still count. After the first run with the check on, any list that BattleMetrics does not list for CBL's token has been posted about, and is fetched but not swept until BattleMetrics lists it:

```sql
SELECT banList, lastError FROM BanListSyncs WHERE state = 'access_lost';
```

**CBL's own export ban lists.** Importing one of CBL's BattleMetrics export ban lists would feed the players CBL exports back in as new bans, which would keep them on the export ban lists. A list whose source is the BattleMetrics ID of any export ban list, compared as the bot compares them when a source is added, is never fetched or swept, and is posted about once. Its bans are kept as they are: the importer only removes a ban when the list's own complete fetch no longer has it, so removing these is left to an admin, with `/banlist remove`, which removes the list and its bans and queues their players for an update. The bot refuses such sources, but lists from before it, or changed by hand, may still have one; to list them:

```sql
SELECT banList, storedCount FROM BanListSyncs WHERE state = 'self_import';
```

A list whose type or source is changed, e.g. with `/banlist update`, starts afresh: what was known about its old source, such as its failures, is forgotten, and the bans of its old source are replaced by those of its new one (see [Removing bans](#removing-bans)). A list's row is deleted with the list.

## Importing a ban list

A list read in full is fetched in full, or not at all. Its stored bans are then read with one query and compared with the bans fetched, and only the bans that are new or changed are written: a ban's player, expiry, whether it has expired, its reason, raw reason and note are compared, a time by its milliseconds, `1` and `0` as true and false, and a missing note as `NULL`. So a run in which nothing changed writes no ban at all. The bans are written 500 at a time, each batch in one transaction, which adds the players that are new and queues the players of the new and changed bans for an update of their Steam profile, reputation and export bans. A batch that ends in a deadlock or a lock wait timeout is run again as a whole, after 5 seconds, for up to 5 attempts in all, as is one that finds the database unavailable. A batch that fails for another reason is written again one ban at a time, so only the bans that cannot be saved, e.g. one with a reason too long for its column, are left out: they are counted, and fetched again by the next run.

**SteamIDs.** A BattleMetrics ban's SteamIDs are its `steamID` identifiers that hold a SteamID64 of a player's account: exactly 17 digits, not part of a longer number, in the range of players' accounts, on their own or in a profile's address, with spaces around them or in any case, or else in the profile's details. A ban without one is skipped. A new ban is for the first SteamID an admin added to it by hand, or else its first. A ban that is stored keeps its player while that is still one of its SteamIDs, whatever their order. Once its player is no longer one of them, e.g. as its partner corrected the SteamID, the ban would move to the SteamID a new ban would be for. Such moves are only counted and logged, in the console and the run record's `moves`, until `IMPORTER_APPLY_STEAMID_MOVES=1` applies them, queueing both the old and the new player for an update. Meanwhile the ban's other changes are still saved.

**Read in full.** A BattleMetrics list is read by following its links to its last page, newest bans first (with head polls off, in BattleMetrics' own order, as before head polls), for at most as many pages as BattleMetrics' count of its bans needs, and 50 more. Each page, of a read in full or a head poll, asks for the list's expired bans as well as its running ones, with `filter[expired]=true`, on the pages its links lead to as on its first, whatever a link gives for it. BattleMetrics' API documentation says that expired bans are hidden without the filter, although BattleMetrics gives them without it too, and a read without them would make the list's expired bans look removed, while BattleMetrics' count of its bans would leave them out as well, so the count check would not notice. BattleMetrics answers a page in about half a second as a rule, but at times does not answer one at all, not even with its headers, while it often answers the same page at once a few seconds later, and in its rare slow spells answers slowly, the slowest seen in 29 seconds. So each page, of a read in full or a head poll, is asked for up to 5 times: each attempt is cut off after 30, 15, 15, 20 and 30 seconds, and the next is made about 1, 2, 2 and 4 seconds later. The first has the 30 seconds of BattleMetrics' other requests, so a slow answer is taken at once, and a page it gets no answer to is asked for again soon after, by shorter attempts, as such a page is answered within a second when it is answered at all; the last two are longer, for a slow spell. A page that is not answered by then, in at most about 121 seconds, fails its list, which is tried again after the other lists. With the count check on (`IMPORTER_SCAN_COUNT_CHECK`, the default), the read is complete only if the number of different bans it read, with or without a SteamID, is no more than 2 short of BattleMetrics' count on its first page, plus however much that count changed by its last page. A read that found more bans than the count may be over it by that, and by 5 more, or 0.5% of the count if that is more: bans that were read cannot be missing, and one production list gives 3 more bans than its count on every read. Bans added or removed while a list is read change its count by little, so BattleMetrics' counts on the pages of one read may differ by at most 10, or 1% of the first page's count if that is more: a read whose counts differ by more, e.g. as a page counts no bans, is not complete either, as its count cannot be trusted. A read that is not complete still saves its new and changed bans, but removes none, and the list fails, so it is tried again after the other lists, and its row counts the incomplete read in `incompleteScans`. A list whose last run did not read it in full either is not tried again in the run, and its failure only goes to the console, as the first was posted and the alert for 3 failed runs in a row says if it lasts. A list that gives no bans on its first page but counts some has not emptied, whether the check is on or not: BattleMetrics answers so when CBL may see a list but not its bans (see [Ban list states](#ban-list-states)).

If BattleMetrics' count of one list stays off, `IMPORTER_SCAN_COUNT_CHECK_SKIP` can name it, to leave it out of the check: a list it names that is read to its last page counts as complete, and is read for up to 2,000 pages, whatever its count. A list that only gives a few more bans than its count needs no such setting. If BattleMetrics' counts stop matching its bans for every list, every list fails until `IMPORTER_SCAN_COUNT_CHECK=0` turns the check off for all of them.

**Remote lists.** A remote list's file is downloaded whole, with time and size limits. Once the list has been imported from a file in full, with nothing kept back, its row keeps the file's `ETag` and `Last-Modified`, if its host gives them, and its SHA-256. The next run asks the host whether the file has changed, with `If-None-Match` and `If-Modified-Since`, and an answer of `304 Not Modified`, or a file with the same SHA-256, means it has not: its bans are not written again, but whether each has expired is brought up to date. A list whose import failed, or kept any of its bans back, forgets its file, so the next run reads it in full, as does a list whose bans are being replaced.

### Head polls and full reads

A BattleMetrics list is read in full only when it needs to be. Otherwise only its newest page is read, 100 bans, newest first, with one request: a head poll. The poll saves the new and changed bans on the page, as a read in full does, but removes none, as only a read of every page can show that a ban is gone, unless the list's type or source was changed while it was polled (see [Removing bans](#removing-bans)). A list's row keeps the IDs of the bans on its newest page, with or without a SteamID, and BattleMetrics' count of the list's bans, from its last read (`headUids`, `headTotal`), which its next poll compares its own with. A poll saves them only once it has saved all the bans it found: a run asked to stop while a poll saves its bans keeps the list's row as it was, so the next poll still finds the bans not saved, as new bans or by drift (see below). A run that only polls makes one request a list, 20 for 20 lists, and its import takes seconds, though its later steps still take as long as on any run (see [Running more often](#running-more-often)).

A list is read in full, rather than polled, for the first of these reasons that applies, which its `reason` in the run record gives, and lists are read in this order: those only polled first, so their new bans are saved within seconds of the start, then those read in full, by the order of their reasons, and of those read in full as their time has come (`periodic`, `every_run` and `remote`), the one read in full longest ago first. So when cycles stop at their time limit before they have read every list that is due, e.g. while BattleMetrics is slow for hours, each starts with the lists the one before left, rather than leaving the lists with the highest IDs every time.

| Reason      | When                                                                                                                                                                                                                                                                                                  |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `new`       | It has not been read in full from its current source yet, or its row has no newest page to poll against, e.g. as it was last read with head polls off.                                                                                                                                                |
| `source`    | Its type or source was changed, so its old source's bans are being replaced.                                                                                                                                                                                                                          |
| `resume`    | An admin resumed it after it was suspended, and it has not been read in full since (see [Paused ban lists](#paused-ban-lists)).                                                                                                                                                                       |
| `removal`   | Bans it no longer had wait for a confirming read, and the first of them is due, 10 minutes after the read that first missed it, or an admin allowed it to lose bans: `IMPORTER_ALLOW_MASS_REMOVAL` names it, or its row's `allowFullRemovalUntil` has not passed while it has bans held for an admin. |
| `drift`     | A poll found that BattleMetrics' count of its bans is not its count at its last read plus the new bans on the pages the poll read.                                                                                                                                                                    |
| `overflow`  | A poll found only new bans on 10 pages.                                                                                                                                                                                                                                                               |
| `periodic`  | Its slot has come (`nextFullScanAt`, see **Schedule** below), or its last full read (`lastFullScanAt`) is older than a list may wait for its slot.                                                                                                                                                    |
| `every_run` | Head polls are off (`IMPORTER_HEAD_POLL=0`), so every list is read in full on every run.                                                                                                                                                                                                              |
| `remote`    | It is a remote list, whose file is asked about on every run.                                                                                                                                                                                                                                          |

**Drift.** Bans added on top of a list add as much to BattleMetrics' count as to the new bans on its newest page, so a count that differs from the one at the list's last read plus the new bans means that something else happened: a ban was removed, from the newest page or below it, or added or moved below it, e.g. as it was backdated. The list is then read in full in the same run, on from the newest page, which is not read again, and the bans the poll found new are saved with the rest of the list, so its losses are measured against the bans it had before the run, as for any read in full. Should that read fail, they wait for the list's next read in full, which the run's second attempt at it, or the next run, makes. A ban counts as new when it is neither stored nor among the newest page's IDs at the last read, and the IDs and counts are BattleMetrics' own, with or without a SteamID, so bans without one, which are never stored, make no false drift. An edit to a ban below the newest page, and a removal that a backdated addition cancels out between two runs, wait for the list's next periodic full read. `IMPORTER_DRIFT=0` keeps the polls but stops comparing the counts, for a time when BattleMetrics' counts cannot be trusted: removed bans are then found only by the periodic full reads, so make those more frequent, e.g. with `IMPORTER_FULL_SCAN_MINUTES=15`.

**Bursts and overflow.** A poll whose newest page holds only bans it has not seen follows the list's pages, newest first, until a page holds one it has, so a burst of new bans, e.g. 150, is saved with a request a page and nothing else. After 10 pages of new bans, the list is read in full instead, on from the pages the poll read (overflow), as so many new bans can mean the list was replaced. The poll saves none of them: the read in full does, so a list whose source now gives none of its old bans, only more than 1,000 new ones, is held for an admin as any read in full would hold it (see [Removing bans](#removing-bans)). A list whose newest page, or the pages a poll followed, reach its last page has been read in full by its poll, so a list of 100 bans or fewer is read in full on every run, with one request.

**Schedule.** Each BattleMetrics list has a slot in every `IMPORTER_FULL_SCAN_MINUTES`, 30 minutes by default: the lists, in the order of their IDs, share the 30 minutes in proportion to their pages, one for about every 100 bans of BattleMetrics' count at their last read, and each list's slot is the middle of its share. The intervals are counted from midnight UTC, so every run, and a restart, finds the same slots. How often runs start is `IMPORTER_CYCLE_SECONDS` in loop mode, whatever `IMPORTER_CADENCE_SECONDS` says, and `IMPORTER_CADENCE_SECONDS` in once mode, so keep that at how often the script starts a run. With runs less than `IMPORTER_FULL_SCAN_MINUTES` apart, as the importer service's cycles, a list read in full is next due at its slot, its row keeping when in `nextFullScanAt`, with `scanReason` `periodic`: the slot that comes at least half of `IMPORTER_FULL_SCAN_MINUTES` less a cadence after the read, so at most 1.5 times `IMPORTER_FULL_SCAN_MINUTES` less a cadence after it, 5 to 35 minutes with a cycle every 10 minutes, and with runs more than half of `IMPORTER_FULL_SCAN_MINUTES` apart, the first slot after the read. So each cycle reads in full the lists whose slots came since the cycle before, about its share of all the lists' pages, a third of them with a cycle every 10 minutes, though a list is always read whole, so a large list's cycle reads more and the cycles next to it less. A list read in the cycle after its slot, even minutes into it, is due at the same slot 30 minutes later, and with cycles at most half of `IMPORTER_FULL_SCAN_MINUTES` apart, the cycle that reads a list again starts within 1.5 times `IMPORTER_FULL_SCAN_MINUTES` of its last full read. After a cycle that read many lists at once, the first one, or the first after a long gap, each is due at its own slot, some sooner than 30 minutes after the read and some later, so within about 30 minutes their full reads are spread over the cycles again, and they stay so. With runs at least `IMPORTER_FULL_SCAN_MINUTES` apart, such as every 6 hours, or every 30 minutes with the default, a list read in full is next due `IMPORTER_FULL_SCAN_MINUTES`, less a tenth of it, after its run planned its reads, as the next run plans its own, so the next run reads it in full again, however late in its run it was read, also when that run starts a little early: every such run reads every list in full, as before slots. When bans it no longer had wait for a confirming read, it is due when the first of them can be confirmed, 10 minutes after the read, with `scanReason` `removal`. A list whose read in full fails stays due one. A poll that found drift or overflow, when the list then cannot be read in full, leaves the list due at once, with that reason, so the next run reads it in full, and so does the run's own second attempt at it. None of these, nor a new or replaced source, waits for a list's slot. A list whose last full read is older than it may wait for its slot, 1.5 times `IMPORTER_FULL_SCAN_MINUTES` less a cadence, 35 minutes with a cycle every 10 minutes, or `IMPORTER_FULL_SCAN_MINUTES` with runs half of that apart or more, is read in full however its row was scheduled, e.g. after `IMPORTER_FULL_SCAN_MINUTES` was made shorter; polls only save requests when runs are closer together than `IMPORTER_FULL_SCAN_MINUTES` (see [Running more often](#running-more-often)).

`IMPORTER_HEAD_POLL=0` turns polls off: every list is read in full on every run, in BattleMetrics' own order, as before head polls, and its row forgets its newest page, so once polls are on again each list is read in full once more first. With both `IMPORTER_HEAD_POLL` and `IMPORTER_DRIFT` off, the importer reads every list as it did before head polls.

### Removing bans

Bans a list no longer has are removed only after a complete read of it, never after a poll of its newest bans, while the run holds its run lock, and never from a list CBL cannot read, or one that imports a CBL export ban list. The bans the list had before the read that the read did not find are missing, and then:

- With `IMPORTER_ALLOW_MASS_REMOVAL` naming the list, or while an admin allows it to lose all its bans (its row's `allowFullRemovalUntil` is a time that has not passed), every missing ban is removed at once.
- A read that found no bans at all, while the list has some, keeps them all, as the list may be broken, and so does a read that found none of the bans of a list of at least 10. The list is `held`, and its line, posted on every run while it is, says to confirm with `IMPORTER_ALLOW_MASS_REMOVAL`. An admin can also allow it in the database, here for two hours: `UPDATE BanListSyncs SET allowFullRemovalUntil = UTC_TIMESTAMP(3) + INTERVAL 2 HOUR WHERE banList = <id>;`
- A read that lost a large part of a list's bans at once keeps them too, for an admin: at least 25 bans, and a fifth of the bans the list had before the read, of those no earlier read had missed. Every read asks BattleMetrics for the list's expired bans too (see [Importing a ban list](#importing-a-ban-list)), so they are not left out as BattleMetrics' documentation describes; this hold is the backstop for any source that suddenly leaves out a large part of a list all the same, e.g. one that stops giving its expired bans. Such a source gives a count that drops with them, so the count check still passes, and only the size of the loss shows it. A list loses a handful of bans a day, a few at a time, so neither is near a day's removals: the 25 decide for a list of up to 125 bans, and the fifth for a larger one, e.g. 2,356 bans of 11,780, while a list's expired bans can be most of it. The list is `held`, as `large`, and its line, posted on every run while it is, says how many of its bans must still be missing for the hold to last, and to confirm with `IMPORTER_ALLOW_MASS_REMOVAL`, or with `allowFullRemovalUntil` as above. Bans that were already waiting for a confirming read, those a hold that ended let go, and those of a list whose source is being replaced are never held so. A list already held that loses such a large part of its other bans, or all of them, holds them with its own (see below).
- A list held as its read found none of its bans, though it found others, or as it lost a large part of them, has its bans recorded in `BanListPendingRemovals` as held, from when that began (`heldAt`), and why, `full` or `large`, in `BanListHolds`, with how many bans the list had before that read. The bans the read found are still saved, so the list then has other bans too, but it stays held, as it began, and its line says since when, until an admin confirms it, which removes the held bans, or until its bans come back. The held bans still missing then wait for a later complete read, as if first missing then, by the rule below, as they do when the list's source is replaced, and the line of the read that ended the hold is posted, with how many came back and when the rest are removed. Of its other bans, those it no longer has are removed by the rule below, unless those of them no earlier read had missed are a large loss by the numbers above, or the list loses all of its bans while it is held as `large`. The hold then takes in every missing ban, those waiting for a confirming read too, held anew, from then, as `large`, and the line says so as a hold that begins. A `large` hold that takes them in is measured as before. A `full` hold that takes in a large loss becomes `large`, measured against the bans it held: so it keeps those at least until one of them comes back, as it would have, and after that until fewer than the fewest are missing, where the `full` hold would have let them go, and it keeps the large loss while enough of it is still missing. Kept as `full`, the large loss would have been let go as soon as any one held ban came back. A `full` hold whose list then loses all of its bans goes on as `full`, holding them all, when too few of them are bans it saved since to be a large loss, so it ends when any one of them comes back, one of the bans it saved since too. How many of its bans must come back for the hold to end depends on why it began:
  - `full`: any one of them, once a complete read finds it again.
  - `large`: enough that fewer than the fewest are still missing, by the numbers above, of the bans it is measured against: 25, or a fifth of them, e.g. fewer than 40 of the 80 a list of 200 lost. A hold that took in a `full` hold of fewer than 25 bans keeps all of them as its fewest. A `large` hold is measured against the fewer of the bans the list had before the read that began it, and those it has before each read since, and `BanListHolds` keeps the fewest it has been measured against. So the bans the list gains do not count, and its growth never ends the hold, also once it has shrunk, while a list that shrinks keeps its hold as one that began on the smaller list would. A held ban that a complete read finds again is no longer held, and loses its record, and the list's line says how many came back, but the others stay held, as they were. Should that ban be missing again later, it is removed by the rule below, as the list's other bans are, unless those missing again with it, and others no earlier read had missed, are a large loss, which the hold takes in as above. As each read writes what it changes of a hold whole (below), a `large` hold starts every read with at least the fewest held, so only its bans coming back end it, besides an admin or a new source. A hold of exactly the fewest ends as soon as one of them comes back.
- Otherwise, fewer than 10 missing bans, and 5% of the list's bans, are removed at once. More are recorded in `BanListPendingRemovals`, and kept, until a complete read at least 10 minutes after the first one that did not have them still does not, when they are removed. The list is due that read 10 minutes after the first, so the first run that starts after then reads it in full, which with runs an hour apart is the next run, and until then it is only polled. A recorded ban that a read finds again loses its record, and when fewer than 10, and 5% of the list, would still wait, they are removed at once. A read that removes a large part of the list's bans so, by the numbers above, e.g. those of a list held as it lost all of them once one came back, posts its line, which says so right after its counts, whatever else it says; of a read an admin confirmed, only the bans it would have removed without the confirmation count.

Each batch of at most 500 bans is removed in one transaction, which also queues their players for an update and drops their records in `BanListPendingRemovals`, and a line about a removal cut short says how many it removed. What a read changes of a hold is written in one transaction, however many bans it holds: as it begins, why, with all of its bans; as it goes on, the records of its bans that came back, with the count it is measured against when that drops; as it takes in more, their release and all of its bans, held anew; and as it ends, the records of its bans that came back, the release of the rest, and its row in `BanListHolds` deleted, or saved for a hold that begins in the same read. An admin's confirmation ends a hold so before any of its bans is removed. So a run cut short in one, e.g. by a database outage longer than the retries or the process being killed, writes none of it, and the next complete read finds the list held as it was, or not at all. The read's new and changed bans are saved before that, though, and a run asked to stop by then stops before it, with those of them it saved. The next complete read then measures the same loss against a list that includes the bans saved: a loss just over the numbers above may no longer be held, and a total loss whose read saved bans it found may be held as `large` instead, or no longer held. A loss no longer held is removed by the last rule above, after its confirming read, or at once when few enough would wait. The rest of a hold an admin confirmed, whose removal was cut short, wait for a confirming read, which removes them. Bans that are new or changed are never kept back.

**Replaced sources.** A list whose type or source was changed since it was last imported, e.g. by hand in phpMyAdmin, may still have its old source's bans. Its new source's bans replace them: they are removed by the rules above, but never held for an admin, though the list seems to have lost them all. Its row's `replacePending` says that the replace is under way, until none of the old bans is left. `/banlist update` deletes the old bans itself, so its lists have none to replace. A list whose type or source is changed while it is being imported, whether it is read in full or polled, has the bans fetched from its old source removed once they are saved, as `/banlist update` may have deleted the list's bans just before the run saved them, and its new source is imported on the next run. That is so also when the run is asked to stop while it saves them: it reads the list again before it stops, and removes them first if the list was changed.

**Dry runs.** With `IMPORTER_DRY_RUN=1`, a run reads what any run would, polling the lists that are not due a full read, and writes nothing: no ban, player, record of a missing ban or `BanListSyncs` row, and it runs none of the other steps, as they all write. As it saves no row, the next run reads and polls the lists as if it had not run. Its counts, in its summary line, status and record, say what the import would have done, and the console has a line for each ban it would add, change, move or remove, up to 100 of each for each list. It posts that it is a dry run, so one left on by mistake is seen, but nothing about the lists. It still takes the run lock, applies the importer's migrations and saves its run record, but never counts as a success for the stale alert. An invalid value, e.g. `0 # done` (`docker run --env-file` keeps a comment after the value), fails the run, with exit code 1, before it imports anything, as it cannot tell whether it may write.

## Expired bans

Whether a ban has expired is stored with it, in `Bans.expired`, which the export ban lists and the website's active and expired bans read. The import sets it for the bans it fetches, but the bans of a list it does not fetch, e.g. as its source is failing or it imports a CBL export ban list, would otherwise stay active for as long as that lasts, and a ban that expires after its list was fetched stays active until the next run fetches it. So after the import, the run marks as expired every ban whose expiry has passed but that is not marked expired (`0` or `NULL`), whatever its list. One read, which locks nothing, finds them, and each batch of 500 is marked in one transaction, which also queues the bans' players for a recalculation of their reputation points and rank and their export bans, by setting their `lastRefreshedReputationPoints`, `lastRefreshedReputationRank` and `lastRefreshedExport` to `NULL`, but not for a refresh of their Steam profile, as their bans did not change. A ban changed since the read is left as it is. A batch that ends in a deadlock or a lock wait timeout, or finds the database unavailable, is run again as a whole, after 5 seconds, as the import's batches are. A dry run does not mark any, as it writes nothing.

The expiries are compared with the time the step starts, given in UTC, as the importer writes every time in UTC, so the comparison is right whatever the time zone of the database or of the connection. In a session in the server's own zone, e.g. `SYSTEM` on a host in Chicago, `NOW()` would be 5 or 6 hours behind, and the bans that expired in that time would not count as expired yet; Sequelize sets the importer's own connections to UTC. To count the bans the next run will mark:

```sql
SELECT COUNT(*) FROM Bans WHERE (expired = 0 OR expired IS NULL) AND expires <= UTC_TIMESTAMP();
```

## Steam profiles

Each run refreshes the Steam profiles, the names, profile addresses and avatars, of the players who were never refreshed, or were queued for a refresh as their bans changed, the newest first, as the export ban lists' alerts name the players they add. After them, it refreshes players whose profile is due a refresh, in the order of their IDs, carrying on after the last one the run before took, which `ImporterState` keeps as `steamRefreshCursor`, and from the first again once it has reached the last. A profile is due a refresh 7 days after its last one, give or take a day: each player has their own interval, from 6 days up to 8, which comes from their ID (`6 days + CRC32(id) % 172800 seconds`), so the players refreshed in the same run fall due over two days, rather than all in one run week after week.

A run refreshes at most `IMPORTER_STEAM_REFRESH_PER_RUN` players due a refresh, and 300 new players besides. When there are more new players, e.g. after a ban list was added, they also take the slots of the players due a refresh, so a run refreshes up to 300 plus `IMPORTER_STEAM_REFRESH_PER_RUN` new players; the slots new players leave unused are not given to players due a refresh. Unless it is set, `IMPORTER_STEAM_REFRESH_PER_RUN` is worked out each run from the number of players and `IMPORTER_CADENCE_SECONDS`: enough to refresh every player within the shortest interval, 6 days, with a run every `IMPORTER_CADENCE_SECONDS`. That is about 15% more than intervals of 6 to 8 days need, so the players Steam leaves out, and those a run could not take, e.g. as Steam was down, are caught up on. For about 145,000 players it is about 6,050 a run every 6 hours (61 calls, about a minute and a half), 1,010 every hour and 250 every 15 minutes. It is at least 200, so that runs a minute or two apart still catch up quickly, and at most 10,000. So keep `IMPORTER_CADENCE_SECONDS` at how often runs really start. The console says how many a run takes (`taking at most 6046 due a refresh a run`), and once runs have caught up, the Steam profiles in the run's status show few or none `left for later runs`.

Steam is asked for 100 players a call, and each call's profiles are saved with one statement, which updates the players' rows and marks them refreshed, and never adds a row for a player removed in the meantime. A player Steam leaves out of its answer, e.g. as the account no longer exists, is tried again a day later rather than on every run: it is marked refreshed a day less than its interval ago, e.g. 6 days ago for a player refreshed every 7 days, and keeps its name. A player whose ID is not a SteamID64 of a player's account, e.g. one saved before SteamIDs were checked, is never sent to Steam: it is skipped and marked as looked at, so it comes up again only once its interval has passed. A profile that cannot be saved, e.g. as its name holds a character the table's character set cannot store, is left out, as the call's other profiles are saved again one at a time; it is tried again a day later, and the run posts how many profiles could not be saved, with the first error.

A call that fails, or is answered without a list of players, is posted with its error, and its players stay as they were, so they are taken again: the new ones as new, and the next run carries on from before the first of those due a refresh. Once 2 calls in a row have failed, the step stops, as Steam is then most likely down, and it stops at once when Steam refuses the API key, or still answers HTTP 429 after the Steam client's own retries and pauses. Nothing waits between calls but the Steam client's limit of one request every 1.5 seconds, and each request has 15 seconds to be answered.

## Reputation points, ranks and export bans

After the Steam profiles, each run clears the reputation points of the players who no longer have any ban, recalculates the reputation points of the players queued for it, and ranks every player, each with one statement on its own, and then recalculates every player's export bans, 250 players a batch: a read of the export bans they qualify for, in a transaction of its own, and one statement for each kind of change. These statements lock the players and bans they read or write. The bot's commands that delete ban lists' bans, such as `/banlist remove` and `/org remove`, which do not wait for the importer, lock some of the same rows in another order, so MySQL may end one of the importer's statements in a deadlock, which rolls back its transaction, or end one that waited too long for a lock. The statement, or the transaction it was in, is then run again as a whole after 5 seconds, up to 5 times in all, as the import's batches are, so the run goes on rather than failing. Each can be run again: the points, ranks and export bans are worked out afresh from the bans, and each write of export bans changes only those that are still as the batch read them.

## Reputation check

A player's reputation points, and from them their rank and risk rating, are recalculated only when the player is queued for it: the import queues the players whose bans it adds, changes or removes, the expiry step those whose bans expire, and the bot's `/banlist remove` the players of the lists it removes, before it deletes their bans. Bans removed any other way queue nobody. A ban list deleted by hand, e.g. in phpMyAdmin, takes its bans with it, as the database deletes a list's bans with the list, so its players keep the points of bans they no longer have, and the rank those points give, until something else queues them.

So once every `IMPORTER_REPUTATION_CHECK_HOURS`, 24 by default, a run checks every player's points against their bans. The points are worked out from the bans by one rule, which the recalculation follows too, as both are built from it in `src/reputation-points.js`, so the two cannot drift apart: on each ban list, a player scores 3 points when any of their bans there has not expired, as it has no expiry or its expiry has not passed, and 1 point for each of their bans there that has, and their points are what they score on all their lists together. Points are not split by game. The check works out every player's points in one statement, which reads without locking anything, and queues the players whose stored points differ, a player with no bans counting as 0 and one with no points stored (`NULL`) as different, for a recalculation of their points, rank and export bans, by setting their `lastRefreshedReputationPoints`, `lastRefreshedReputationRank` and `lastRefreshedExport` to `NULL`, as the expiry step does, but not for a refresh of their Steam profile. It queues them 500 at a time, each batch one statement by ID, which is run again after 5 seconds when it ends in a deadlock or a lock wait timeout, e.g. with the bot queueing the same players, as the import's batches are, and queues at most 1,000 a run, the first by ID, as the recalculation after it holds up other writes while it runs (see **Cost** below): the others are left for the next runs, which check again until none are left. A player who is queued already is left out, as the recalculation takes them anyway. The check runs right after the expiry step, which queues the players whose bans' expiry has passed, so a ban that has just expired is not taken for a removed one, and before the steps that recalculate players, so the players it queues are recalculated in the same run.

When it queued players, it posts how many to the log channel, with up to 5 of their Steam IDs, their stored points and the points their bans give, as it means bans were removed, or changed, without queueing their players, e.g. as a ban list was deleted by hand rather than with `/banlist remove`, and how many it left for the next runs, if any. Each ID is shown as written, on one line, as players saved before SteamIDs were checked can have other IDs, such as a Steam profile's address:

```text
[Reputation][1] Queued 1,000 players for a recalculation, as their reputation points did not match their bans: 7656119xxxxxxxxx1 (9 points, 6 by their bans), 7656119xxxxxxxxx2 (4 points, 0 by their bans), 7656119xxxxxxxxx3 (3 points, 1 by their bans), 7656119xxxxxxxxx4 (no points, 3 by their bans), 7656119xxxxxxxxx5 (6 points, 3 by their bans) and 995 more. This means bans were removed, or changed, without queueing their players, e.g. as a ban list was deleted by hand rather than with /banlist remove. It queues at most 1,000 players a run, so the recalculation after it stays short: the other 2,726 are left for the next runs, as the check is due again until none are left.
```

Its counts say how many players it compared, queued and left (see [The JSON line](#the-json-line)), and so does the run's status, in a run in which it ran: `145,094 players checked, all matched their bans`, or `145,094 players checked, 3,726 did not match their bans, of which 1,000 were queued, 2,726 left for later runs`. A run in which it was not due, or is off, leaves it out. A cycle of the importer service whose check queued players counts as one that changed something, and the players it queued are in the status message's totals and the hourly summary (see [The log channel in loop mode](#the-log-channel-in-loop-mode)).

It compares players' points now, and not their points a month before, nor the change since then, which the website's most harmful players of the month are ranked by. Those change by themselves as bans pass the one-month mark, whether or not anything happens to the bans, and are recalculated only when a player is queued, as they were before the check. Comparing them would queue, every day, every player whose bans passed that mark since they were last recalculated, as if their bans had been removed. A player the check queues has their points a month before recalculated too.

**When it runs.** A run tells whether the check is due from `reputationCheck` in `ImporterState`, which keeps when the run that last checked started: it is due in a run that starts `IMPORTER_REPUTATION_CHECK_HOURS` after that, or later, less 5 minutes, or a tenth of the cadence if that is less, as runs start a little before or after their time. So the first run after the version with the check is deployed checks at once, runs every 6 hours check every 4th run, and the importer service checks in one cycle a day, the first one that starts a day after the cycle that last checked. A run in which it is not due skips it at the cost of reading that row, and says so in its counts, with when it is due (`"ran": false` and `dueAt`). A check that left players for the next runs, as it queued 1,000, or that stopped part-way, e.g. as the run was asked to stop, or failed, saves no row, so the next run checks again, and queues the next players: the importer service works through them 1,000 a cycle, and runs every 6 hours 1,000 a run, until a check finds none left to queue and saves its row. `IMPORTER_REPUTATION_CHECK_HOURS=0` turns it off. Like the other steps, it stops where the run asks it to, before it writes and between batches, and it writes only while the run holds its locks. A dry run does not check, as it writes nothing.

**Cost.** On MySQL 8.0, with 145,000 players and 87,000 bans on 20 lists, the check takes about half a second and locks nothing, and the single-row writes the website and the bot make took no longer meanwhile than without it. The players it queues are recalculated by the reputation step as any queued players are, which takes about half a second plus about 7 milliseconds for each player recalculated, in one statement that locks every `SteamUsers` row, and the bans it reads, until it ends. Meanwhile the website's player pages, which save when a player was last viewed, its sign-ins and other writes to the players and the bans wait for it, and fail once they have waited longer than MySQL's `innodb_lock_wait_timeout`, 50 seconds by default, and the bot's `/banlist remove` and `/org remove`, which try 3 times within about 3 seconds, may end in a deadlock and fail, and need running again. So a run's check queues at most 1,000 players, at most about 8 seconds of that step. After two lists with 21,561 bans of 19,335 players were deleted by hand, 9 cycles queued 8,769 of those players, 1,000 a cycle (the orphaned players step clears the points of every player left with no bans, queued or not), each recalculation took at most 6 seconds, page views waited at most 6 seconds and none failed, and a `/banlist remove` made during the first went through after 5 seconds. With 1,000 players queued, a `/banlist remove` went through 9 times out of 9, waiting at most 8 seconds. Without the limit, the first check queued all 19,328, recalculating the 8,656 who still had bans took 49 seconds, a page view waited 44 seconds and the `/banlist remove` failed with a deadlock, as happens whenever that many players are queued at once by other means, e.g. by a `/banlist remove` of a large list.

## Paused ban lists

An admin can pause a ban list with the bot's `/banlist suspend`, rather than removing it, e.g. while a partner's list is in dispute, and later resume it with `/banlist resume`. The list, its bans, the export ban list configs that use it and its row of `BanListSyncs` are all kept. Its row of `BanListSuspensions` says it is paused: suspended, until it is resumed, and then resuming, until the importer has caught up with it.

- **Suspended.** The importer does not import it at all: it is not fetched, given no slot for full reads, checked for access nor posted about, and the run's counts say how many lists it left out (`suspended`). Its bans count for nothing: not toward players' reputation points, now or a month before, so a pause does not show as a change over the month, nor their rank or risk, nor any export ban list, and the website leaves them out of its lists of bans and ban lists, but shows them, marked, on players' own pages.
- **Resuming.** The importer imports it again, and reads it in full at once (`resume`), while its bans still count for nothing. Once a read in full of it has completed since it was resumed, and that read left no bans waiting for a later read to confirm that they are gone, and none held for an admin as the list seemed to have lost all its bans, or a large part of them at once, the importer has caught up with it: it deletes its row, unless the list was suspended or resumed again since, posts that the list counts again, and names it in the run's counts (`caughtUp`). So the bans its owner lifted while it was suspended never count again: they are removed first, by the reads that confirm they are gone (see [Removing bans](#removing-bans)). A list that cannot be read, e.g. as CBL lost access to it, stays resuming.

Every step of a run, or of a cycle of the importer service, leaves out the same lists, as the first step that needs them reads them once, after the run's migrations, and gives them to each statement as their IDs. A list paused or resumed while a run is under way is seen by the next run. With no list paused, every statement is the one from before lists could be paused.

**Players.** The players of a list that is paused, or counts again, are not queued at once: a large list's players, all recalculated in one statement, would hold up the website for as long as a minute (see **Cost** in [Reputation check](#reputation-check)). Export bans follow on the next run, as every player's are recalculated every run. Players' reputation points follow by the reputation check, which is due, whenever it is next due by time, also as soon as a run leaves out other lists than the ones its row says it last left out (`excludedBanLists`), or while players it found then are left (`pending`), even with `IMPORTER_REPUTATION_CHECK_HOURS=0`, which turns off only the daily check. As every ban counts for at least a point, it finds every player with bans on the list, and queues them 1,000 a run, so a list of 9,000 players settles over 9 runs, or cycles. Its row names the lists the players it queued are recalculated without, so a list resumed before all its players were settled has those already recalculated found again. Its line in the log channel says which lists were paused, or count again, since it last checked.

The website's export ban list size check counts the bans of paused lists too, so an export ban list cannot be given more points while a large list is paused and go over its cap when it counts again, and the website gives a paused list no new export ban list configs.

The bot's `/banlist remove`, `/org remove` and `/banlist update` with a new source delete a paused list's bans without queueing its players once the reputation check has settled them without those bans, as its row says, as deleting them then changes no player's points. A list paused since the check last ran has its players queued, as any list's are.

**Limits.** A resuming list that cannot be read, e.g. as CBL lost access to it, or that seems to have lost all its bans, or a large part of them at once, stays resuming, so its bans count for nothing, until access comes back, or an admin confirms the removal or its bans come back, as above; `/banlist status` shows its state. A list that imports one of CBL's own export ban lists is never read, so its resumption ends at once. A read in full of a resuming list that completes but then fails, e.g. while removing bans, counts as read in full, so the list waits for its next full read, at its slot, rather than the next run. Only the reputation check settles paused lists' players' points, so it must stay among the run's steps.

```sql
SELECT banList, suspendedAt, suspendedBy, reason, resumedAt FROM BanListSuspensions ORDER BY banList;
```

## Database tables

Besides the CBL's own tables, the importer owns `ImporterSchemaMigrations`, `ImporterState`, `BanListSyncs`, `BanListPendingRemovals`, `BanListSuspensions` and `BanListHolds`. It makes them itself with its migrations (`src/schema/migrations.js`), which it applies once it holds the run lock, before its first step, and records in `ImporterSchemaMigrations`, and the importer never changes the CBL's own tables' columns or indexes. The web server and the bot never make or change these tables. They write only these rows, listed in `scbl-lib/db/models/importer/index.js`, where any other is to be listed too:

- `ImporterState`: the row `lastLogMessage`, which the web server and the bot write.
- `BanListSuspensions`: the bot adds the rows, sets their `resumedAt`, and suspends a resuming list again by setting its `suspendedAt`, `suspendedBy` and `reason` anew and clearing its `resumedAt`; the importer deletes them. A list's row also goes with the list, by its foreign key, when the bot removes the list.

A migration that fails makes the run fail with exit code 1, naming the migration. Going back to an older importer image leaves the tables in place, and the older importer ignores them.

| Migration                       | What it makes                                                                                                                                                                 |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `001-importer-state`            | `ImporterSchemaMigrations` and `ImporterState`.                                                                                                                               |
| `002-ban-list-syncs`            | `BanListSyncs`, with a foreign key to `BanLists`, so a list's row is deleted with the list.                                                                                   |
| `003-ban-list-pending-removals` | `BanListPendingRemovals`, with a foreign key to `BanLists`, and a ban's ID with the type, character set and collation of `Bans.id`, which it refers to without a foreign key. |
| `004-ban-list-suspensions`      | `BanListSuspensions`, with a foreign key to `BanLists`, so a list's row is deleted with the list.                                                                             |
| `005-ban-list-holds`            | `BanListHolds`, with a foreign key to `BanLists`, so a list's row is deleted with the list.                                                                                   |

A migration waits at most 3 seconds for a table that another connection is using, e.g. in a transaction left open, and while it waits, other queries on that table wait behind it: for `002` to `005`, the website's and the bot's queries on `BanLists`. If the wait runs out, the run fails, saying what to look for, and the next run tries again. Before deploying a version with a new migration, check that `SELECT * FROM information_schema.innodb_trx;` shows no long-running transactions.

`BanListSyncs` has one row for each ban list the importer has imported, or tried to:

| Column                                               | What it holds                                                                                                                                                                                                 |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `banList`                                            | The list, by `BanLists.id`.                                                                                                                                                                                   |
| `state`                                              | `ok`, `failing`, `held`, `access_lost` or `self_import` (see [Ban list states](#ban-list-states)).                                                                                                            |
| `lastAttemptAt`, `lastSuccessAt`                     | When the list was last fetched, and when it was last fetched in full and its bans saved, in UTC.                                                                                                              |
| `consecutiveFailures`                                | How many runs in a row the list failed to import.                                                                                                                                                             |
| `lastError`                                          | Why its latest import failed, or why CBL cannot read it, which is kept while later runs cannot tell whether it can again: on one line, at most 500 characters, without addresses. Never shown on the website. |
| `storedCount`, `headTotal`                           | The bans the list has here, and BattleMetrics' count of its bans when it was last fetched, or `NULL` for a remote list. A poll's count is saved once the bans on the list's newest page are.                  |
| `lastHeadPollAt`, `headUids`                         | When the list's newest page was last read, by a poll or a read in full, and its bans saved, in UTC, and the IDs of the bans on it, with or without a SteamID, as JSON, which the next poll compares with.     |
| `lastFullScanAt`                                     | When the list was last read in full, in UTC.                                                                                                                                                                  |
| `nextFullScanAt`, `scanReason`                       | When the list is next due to be read in full, in UTC, and why: `periodic`, `removal`, `drift` or `overflow` (see [Head polls and full reads](#head-polls-and-full-reads)).                                    |
| `incompleteScans`                                    | How many reads of all of the list in a row were not complete.                                                                                                                                                 |
| `sourceKey`                                          | A SHA-256 of the list's type and source, by which the importer tells that its source was changed.                                                                                                             |
| `replacePending`                                     | Whether the bans of the list's old source are still being replaced by those of its new source.                                                                                                                |
| `allowFullRemovalUntil`                              | Until when the list may lose all of its bans at once, as an admin confirmed, in UTC. The importer only reads it.                                                                                              |
| `remoteEtag`, `remoteLastModified`, `remoteBodyHash` | For a remote list, the `ETag`, `Last-Modified` and SHA-256 of the file it was last imported from in full, with nothing kept back.                                                                             |
| `updatedAt`                                          | When the row was last saved.                                                                                                                                                                                  |

To have a list read in full on the next run, e.g. after fixing something by hand: `UPDATE BanListSyncs SET nextFullScanAt = UTC_TIMESTAMP(3) WHERE banList = <id>;`

`BanListPendingRemovals` has a row for each ban that a complete read of its list no longer had, which waits for a later complete read to confirm that it is gone, or for an admin, as its list seemed to have lost all its bans, or a large part of them at once (see [Removing bans](#removing-bans)): its list (`banList`), its ID (`banId`), when a complete read first and last did not have it (`firstMissingAt`, `lastMissingAt`), and, for a ban held for an admin, when that began (`heldAt`), in UTC. A list's rows are deleted with the list.

`BanListHolds` has a row for each list whose bans are held for an admin, while they are: its list (`banList`), why (`reason`): `full`, as a read found none of its bans, or `large`, as a read lost a large part of them at once, and how many bans the list had before that read (`storedCount`). A `large` hold's bans still missing are measured against it, so the importer lowers it as the list shrinks while the hold lasts, and a `large` hold that took in a `full` one has the bans that hold held. The runs after the one that began a hold read it, so the `hold` in their records, and the lines they post, still say which hold it is. Every complete read of a list reads its row, and deletes it once the list is no longer held, also when its hold ended without this importer, e.g. as `/banlist update` deleted the held bans, or the previous image ended it. A list held by an importer from before it has no row, and is held as `full`, the only hold that importer kept. The importer writes a list's row, and its held bans, in one transaction, so a `large` hold it keeps starts every read with at least the fewest held, of the fewer of its `storedCount` and the list's bans before the read. A row that says `large` while fewer of the list's bans are held outlived its hold, e.g. as the previous image ended it and then held the list as it lost all of its bans, or as held bans were deleted by hand: they are held as `full`, as they are, and the row is deleted while that hold goes on. The importer alone writes it, and a list's row is deleted with the list.

```sql
SELECT banList, COUNT(*), MIN(firstMissingAt), COUNT(heldAt), MIN(heldAt) FROM BanListPendingRemovals GROUP BY banList;
SELECT banList, reason, storedCount FROM BanListHolds;
```

```sql
SELECT banList, state, lastSuccessAt, consecutiveFailures, storedCount, headTotal, lastError FROM BanListSyncs ORDER BY banList;
SELECT banList, lastHeadPollAt, lastFullScanAt, nextFullScanAt, scanReason FROM BanListSyncs ORDER BY nextFullScanAt;
```

| `IMPORTER_ALLOW_MASS_REMOVAL`     |         | Ban list IDs, separated by commas, that may lose any number of bans at once in the next run, once they are read in full, which removes the bans held for an admin (see [Removing bans](#removing-bans)). | `IMPORTER_ACCESS_CHECK`           | `1`     | `0` turns off the check, once a run, of which BattleMetrics ban lists the CBL organisation can see (see [Ban list states](#ban-list-states)).                                                                                                                                                                                                                                                                                                                  |
| `IMPORTER_SCAN_COUNT_CHECK`       | `1`     | `0` turns off the check that a read of a BattleMetrics list found as many bans as BattleMetrics counts on it (see [Importing a ban list](#importing-a-ban-list)).                                                                                                                                                                                                                                                                                              |
| `IMPORTER_SCAN_COUNT_CHECK_SKIP`  |         | Ban list IDs, separated by commas, that the count check leaves out, for a list whose count BattleMetrics keeps getting wrong. Remove a list from it once its count is right again.                                                                                                                                                                                                                                                                             |
| `IMPORTER_APPLY_STEAMID_MOVES`    | `0`     | `1` moves a ban whose player is no longer one of its SteamIDs to another of them. Until then such moves are only counted and logged.                                                                                                                                                                                                                                                                                                                           |
| `IMPORTER_HEAD_POLL`              | `1`     | `0` turns head polls off, so every list is read in full on every run, in BattleMetrics' own order, as before head polls (see [Head polls and full reads](#head-polls-and-full-reads)).                                                                                                                                                                                                                                                                         |
| `IMPORTER_DRIFT`                  | `1`     | `0` stops polls comparing BattleMetrics' count of a list's bans with its count at its last read and the new bans, so removed bans are only found by the periodic full reads.                                                                                                                                                                                                                                                                                   |
| `IMPORTER_FULL_SCAN_MINUTES`      | `30`    | How often each BattleMetrics list is read in full, in minutes, each at a slot of its own, which spreads the reads over the runs (see [Head polls and full reads](#head-polls-and-full-reads)): a whole number from 1 to 10080 (a week).                                                                                                                                                                                                                        |
| `IMPORTER_STEAM_REFRESH_PER_RUN`  |         | How many players due a Steam profile refresh a run refreshes, at most: `0` to `10000`. Not set, or invalid, with a warning, it is enough to refresh all within 6 days at `IMPORTER_CADENCE_SECONDS`, at least `200` (see [Steam profiles](#steam-profiles)).                                                                                                                                                                                                   |
| `IMPORTER_REPUTATION_CHECK_HOURS` | `24`    | How often the reputation check runs, in hours: a whole number from `1` to `8760` (a year), or `0`, which turns it off. It runs in the first run, or cycle, that starts this long after the one that last checked, less 5 minutes, or a tenth of the cadence if that is less (1 minute for the service's 10-minute cycles), in the first after a deploy, and in every run while players it found are left to queue (see [Reputation check](#reputation-check)). |
| `IMPORTER_DRY_RUN`                | `0`     | `1` makes the run read what it would, write nothing and say what the import would change. It runs no other step.                                                                                                                                                                                                                                                                                                                                               |
| `GIT_SHA`                         |         | The commit the image was built from, shown when a run starts and in its JSON line.                                                                                                                                                                                                                                                                                                                                                                             |

The switches are on with `1`, `true`, `on` or `yes`, and off with `0`, `false`, `off` or `no`, in any case, with spaces or one pair of quotes around them, which `docker run --env-file` keeps. An invalid value of `IMPORTER_ACCESS_CHECK`, `IMPORTER_SCAN_COUNT_CHECK`, `IMPORTER_APPLY_STEAMID_MOVES`, `IMPORTER_HEAD_POLL` or `IMPORTER_DRIFT` is taken as the safer choice, with a warning posted to the log channel: the checks stay on, no ban is moved, polls still compare BattleMetrics' counts, and head polls are off, so every list is read in full. An invalid `IMPORTER_FULL_SCAN_MINUTES` is taken as 30, and an invalid `IMPORTER_REPUTATION_CHECK_HOURS` as 24, each with a warning too. An invalid `IMPORTER_DRY_RUN` fails the run before it imports anything (see the dry runs in [Removing bans](#removing-bans)), as either choice could be the wrong one.

### Deploying the version that writes only what changed

Its first run applies migration `003`. Then:

1. Run once with `IMPORTER_DRY_RUN=1`. The new and updated bans should be near zero, as the import compares what its old versions wrote. Its removals are the bans the lists really lost since the last run, and the moves, in the console and `moves`, are bans whose player is no longer one of their SteamIDs. `SELECT COUNT(*) FROM SteamUsers WHERE id NOT REGEXP '^[0-9]{17}$';` counts the players with malformed IDs from before SteamIDs were checked. Check its summary line for failed lists, and the console for lists that were not read in full (`while checking that it was read in full`), which a dry run does not post: a list whose BattleMetrics count stays off would fail every run, so leave it out of the count check with `IMPORTER_SCAN_COUNT_CHECK_SKIP`, rather than turning the check off for every list.
2. Set `IMPORTER_DRY_RUN=0`, or remove it, and run as usual, with writes on and `IMPORTER_APPLY_STEAMID_MOVES=0`.
3. Once the moves have been reviewed, set `IMPORTER_APPLY_STEAMID_MOVES=1`.

A list that the previous version held, as it would have lost at least 25 bans and 10% of them at once, is no longer waiting for `IMPORTER_ALLOW_MASS_REMOVAL`: its missing bans are recorded on the first run, and removed by the next one that still does not find them, unless it seems to have lost all of its bans. The dry run counts them as held.

Going back to the previous image returns to its rules: a list's missing bans are removed at once, unless they reach 25 bans and 10% of the list, which wait for `IMPORTER_ALLOW_MASS_REMOVAL`. The new table stays, and the older importer ignores it.

### Deploying the version that marks expired bans and budgets Steam profiles

Nothing needs to be set: each run works out how many Steam profiles to refresh from `IMPORTER_CADENCE_SECONDS`, so keep that at how often runs start, e.g. `3600` once they start every hour. The first run may mark many bans expired, those of lists that were not fetched for a while, and queue their players. Within a day, the Steam profiles in the run's status should show few or none `left for later runs`. If `IMPORTER_STEAM_REFRESH_PER_RUN` is set instead, e.g. to keep the Steam step short, about `6100` keeps about 145,000 players refreshed weekly with a run every 6 hours, and about `1000` with a run every hour.

Going back to the previous image brings back its Steam step, which refreshes in one run every player not refreshed for 7 days: a few thousand after runs of this version, which adds a few minutes to that run, and more, for longer, if `IMPORTER_STEAM_REFRESH_PER_RUN` was set lower than the schedule needs. The bans this version marked expired stay marked.

### Deploying the reputation check

Nothing needs to be set. The first run, or the importer service's first cycle, after the deploy checks every player at once, and then once a day. If it posts that it queued players, they are players whose bans were removed without queueing them before the deploy, e.g. those of lists deleted by hand. It queues at most 1,000 a run, which the steps after it recalculate in the same run, in up to about 8 seconds, and the next runs, or cycles, queue the others, 1,000 at a time, until none are left. While that step runs, the website's player pages and sign-ins and the bot's commands that delete bans wait for it, and a `/banlist remove` may fail with a deadlock and need running again (see **Cost** in [Reputation check](#reputation-check)).

To see beforehand how many players the first check will find, run this query, which only reads, e.g. in phpMyAdmin. It counts as the check does, with `UTC_TIMESTAMP()` for the time, as a phpMyAdmin session may not be in UTC:

```sql
SELECT COUNT(*) AS players, SUM(IFNULL(P.points, 0) = 0) AS withNoBansLeft
FROM SteamUsers SU
LEFT JOIN (
  SELECT steamUser, SUM(IF(active > 0, 3, 0) + expired) AS points
  FROM (
    SELECT steamUser, banList,
      SUM(expires IS NULL OR expires >= UTC_TIMESTAMP()) AS active,
      SUM(expires IS NOT NULL AND expires < UTC_TIMESTAMP()) AS expired
    FROM Bans GROUP BY steamUser, banList
  ) L GROUP BY steamUser
) P ON P.steamUser = SU.id
WHERE SU.lastRefreshedReputationPoints IS NOT NULL
  AND NOT (SU.reputationPoints <=> IFNULL(P.points, 0));
```

The orphaned players step of the first run clears, in milliseconds, the points of those with no bans left (`withNoBansLeft`), whether queued or not, and the others, `players - withNoBansLeft`, are queued 1,000 a run, or cycle.

To leave the check off, set `IMPORTER_REPUTATION_CHECK_HOURS` to `0` before the importer first runs an image with the check: in the script's env file for runs in once mode, and for the importer service in its own `environment:` block, as `IMPORTER_REPUTATION_CHECK_HOURS: '0'`, as the stack passes the service only the variables that block names. For a service whose `IMPORTER_TAG` is `latest`, that is before this version is merged, as CI's webhook updates the stack once it has pushed the new `latest`. Going back to the previous image leaves the `reputationCheck` row in `ImporterState`, which it ignores.

### Deploying paused ban lists

Before merging, check that `SELECT * FROM information_schema.innodb_trx;` shows no long-running transactions, as migration `004` makes `BanListSuspensions` with a foreign key to `BanLists`. Until the importer has applied it, the website and the bot see no list paused, and `/banlist suspend`, `/banlist resume` and `/banlist status` say the importer has not created its tables yet. Nothing needs to be set. If the importer service's `IMPORTER_TAG` is pinned, move it on the same day as the web server and the bot, as they share the statements that leave paused lists out.

To go back to the previous images, first resume every paused list, and wait until `/banlist status` shows none paused and a run has checked players' points since (the `reputationCheck` row in `ImporterState` has `"pending": false` and `"excludedBanLists": []`), as the previous importer would import and count paused lists at once, and settle their players only by the daily check. Do not go back with the importer alone while a list is paused: the website would leave out bans the importer counts. Going back leaves `BanListSuspensions` in place, which the previous images ignore.

### Deploying holds of large losses

Before merging, check that `SELECT * FROM information_schema.innodb_trx;` shows no long-running transactions, as migration `005` makes `BanListHolds` with a foreign key to `BanLists`. Nothing needs to be set. From the first cycle after it, a complete read that loses at least 25 of a list's bans at once, and a fifth of them, holds them for an admin rather than removing them after a confirming read: the list is `held`, and its line is posted on every read in full of it, until `IMPORTER_ALLOW_MASS_REMOVAL` names it for one run, or so many of the bans come back that those still missing are no longer a large part of the bans it had, or has, if fewer (see [Removing bans](#removing-bans)). Bans that were already waiting for a confirming read are removed by it as before. A list held before, as it lost all of its bans, stays held as `full`, unless it loses a large part of the bans it saved since, which holds them all as `large` from then.

Going back to the previous image leaves `BanListHolds` in place, which it ignores. It still keeps the bans held as `large` until an admin confirms it or one of them comes back, as it keeps those of a list that lost all of its bans, whose line its own then posts, so a single ban that comes back meanwhile ends the hold, and it holds no new large loss. Nor does it delete a list's row when a hold ends: once this version is back, the list's next complete read deletes it, but a hold the previous image began meanwhile, as a list lost all of its bans, is taken for the one the row names until it ends. For `large`, that lasts at least as long as a `full` hold would, and its lines say `large`, while it holds at least the fewest of the fewer of the row's `storedCount` and the list's bans; with fewer, which such a hold would end at once with none of its bans back, its bans are held as `full`, as they are, and the row is deleted (see [Database tables](#database-tables)).

### Deploying head polls

The version with head polls needs no migration. Deploy it on the 6-hour schedule: its first run reads every list in full, newest first, as no list has a newest page to poll against yet, and takes as long as a run did before, and so does every run after it, as each list's last full read is then older than `IMPORTER_FULL_SCAN_MINUTES`. A list that gives a few more bans than BattleMetrics counts, as list 80 does, now passes the count check, so it can be removed from `IMPORTER_SCAN_COUNT_CHECK_SKIP`. Once a few runs have gone well, move to a run every hour (see below).

To go back to the previous image, first put back in `IMPORTER_SCAN_COUNT_CHECK_SKIP` any list taken out of it for this version, such as list 80, as the previous image's count check fails a list that gives more bans than BattleMetrics counts, on every run. Go back to the 6-hour schedule too: have the script start a run every 6 hours, and remove `IMPORTER_CADENCE_SECONDS` and `IMPORTER_MAX_RUN_SECONDS`, or set them back to their defaults, 21600 and 18000. The previous image reads every list in full on every run, which takes as long as a run did before head polls. It leaves the columns this version fills as they are, and ignores them.

### Running more often

With this version, runs can start every hour:

1. Set `IMPORTER_CADENCE_SECONDS=3600`, so the importer is stale after 3 hours without a successful run.
2. Set `IMPORTER_MAX_RUN_SECONDS=3300`, so a run that is slow stops before the next one starts. A start while a run still holds the lock is skipped anyway (see [Running it](#running-it)).
3. Have the script start a run every hour.

Runs an hour apart still read every list in full on every run, as each list's last full read is then older than `IMPORTER_FULL_SCAN_MINUTES`, so each run takes as long as a run every 6 hours does, about 9 minutes in production, with about 875 BattleMetrics requests. What changes is that new, changed, removed and expired bans reach CBL within about an hour, rather than 6 hours, or about 2 hours for bans removed many at once, which wait for a confirming read on the next run. Polls only save requests when runs come closer together than `IMPORTER_FULL_SCAN_MINUTES`, so on hourly runs only with it longer than an hour: with `IMPORTER_FULL_SCAN_MINUTES=120`, each list is read in full on every other run, at its slot, and only polled in between, so each run reads about half of the lists' pages in full. A removed ban is then still found within the hour, by drift, but an edit to a ban below a list's newest page takes up to 2 hours to reach CBL. So does a ban's expiry there, as a ban is marked expired when it is read, which for a ban below its list's newest page is the list's next full read.

Runs every 15 minutes are for once the importer recalculates only the players whose bans changed. Until then, every run, even one that only polls, still:

- recalculates every player's reputation points and export bans, and sends the export ban lists' changes, about a minute of work in production, 96 times a day rather than 24;
- posts its status message, and a line for each list that fails, so a BattleMetrics outage posts about 20 lines a run, over 80 an hour;
- counts failures in runs rather than in time, so the alert for each list that failed 3 runs in a row comes 45 minutes into a BattleMetrics outage, rather than after 12 hours or more on the 6-hour schedule.

To run every 15 minutes even so, set `IMPORTER_CADENCE_SECONDS=900` and `IMPORTER_MAX_RUN_SECONDS=840`, and have the script start a run every 15 minutes. Each list is then read in full every other run, at its slot, and polled in between, so each run reads about half of the lists' pages in full, about 6 minutes of requests in production, and polls the others: about 1,800 BattleMetrics requests an hour, 30 a minute on average. A new ban on top of a list reaches CBL within one run, a ban removed from a list within one run too, by drift, or up to two runs later when many are removed at once and wait for a confirming read, and an edit to a ban below a list's newest page, or its expiry, within about 30 minutes, and the time the run that reads the list in full takes to reach it.

The importer service runs every 10 minutes by itself, without the script (see below).

## Running as a service

With `IMPORTER_MODE=loop`, the importer runs as a long-running service, the importer service, in the Portainer stack, rather than once each time the script starts it. It takes the service lock once, when it starts, and keeps it, so no other run starts while it runs, and runs a cycle every `IMPORTER_CYCLE_SECONDS`, 10 minutes by default, from the start of one cycle to the start of the next: a cycle that took 2 minutes is followed by the next 8 minutes later, and one that took longer than 10 minutes by the next at once. Each cycle holds the run lock while it goes, and frees it once its record is saved, so the one bot command that is refused while a run is under way, giving a ban list a new type or source, works between cycles (see [The locks](#the-locks)). Each cycle is a run of the importer: it has the same steps and stop points, its record is saved as a run's is, in `ImporterState`, and it prints a JSON line of its own, which also gives its number (`cycle`), the process's memory (`memory`), and in its `phases` how long it waited for the run lock (`takeRunLock`). The first cycle connects and applies the importer's migrations, as a run does, and so does each cycle after it until one has. The cadence, which sets when the importer is stale and how many Steam profiles a cycle refreshes, is `IMPORTER_CYCLE_SECONDS` unless `IMPORTER_CADENCE_SECONDS` is set, and `IMPORTER_MAX_RUN_SECONDS` is not used. The import plans each list's full reads by `IMPORTER_CYCLE_SECONDS`, how often cycles start, whatever `IMPORTER_CADENCE_SECONDS` says.

Until the export recalculation only recalculates the players whose bans changed, each cycle still recalculates every player, about 45 seconds in production, so start the service at a cycle of 10 minutes, as below, rather than at a minute or two. With head polls, each cycle reads in full the lists whose slots came since the cycle before, about a third of all the lists' pages at a cycle of 10 minutes, which takes about 4 to 6 minutes in production, and only polls the others' newest bans (see [Head polls and full reads](#head-polls-and-full-reads)). The first cycle, and the first after a long gap, reads every list in full, which takes about 14 minutes in production.

To see the latest cycles:

```bash
docker logs cbl-importer 2>&1 | grep -F '{"event":"cbl-importer-run"' | tail -n 6 | jq -c '{cycle, outcome, seconds, reason, memory}'
```

### Stops and exit codes

- **Time limit.** A cycle that takes longer than `IMPORTER_MAX_CYCLE_SECONDS`, 15 minutes by default, counted from when it took the run lock, once the database answered, stops at its next safe point, as a run stops at its time limit, and the next cycle starts at once and carries on with the work. A page of bans being read then gets no more attempts, and stops waiting for one, for the budget, a pause or `Retry-After`, within a second, and an attempt already sent is cut off within 30 seconds, so a slow BattleMetrics does not keep the cycle from stopping in time. A cycle that has not stopped 60 seconds after its time limit, e.g. as a step is stuck, ends the service: it posts why, prints the cycle's JSON line and exits 1, after at most 5 seconds for its log messages, and once it has stopped the statements the cycle still has running on the database, as at a stop's deadline (below), for Docker to start it again. Docker never restarts a container that is only unhealthy, so the service exits rather than wait. Its status message and row say that it failed, also when a signal came after the time limit, though Docker then does not start it again, and the service does not say that it will.
- **SIGTERM and SIGINT**, as `docker stop` and a stack update send, stop the cycle under way at its next safe point, or end the wait between cycles at once. The service then shows that it stopped in its status message, saves how it ended, closes the database connections, sends its log messages and releases the locks, and exits 0. A connection that has not closed in time, as its statement is still running, is closed on MySQL's side first (see below). Once the cycle reaches a safe point, all of that takes at most 45 seconds, and less when the safe point came late, so that the service exits within 55 seconds of the signal, inside the 60 seconds of `stop_grace_period`. The next safe point can be minutes away, though, as a BattleMetrics request is sent and answered before it: a request waits for the budget, as a full read of every list or a large export fill can use up the minute's requests, waits a minute once BattleMetrics says few of the key's requests are left, or as long as BattleMetrics asks after it answered 429, up to 5 minutes, and is made up to 3 times when BattleMetrics does not answer, each attempt cut off after 30 seconds, or, for the import's reads of pages of bans, up to 5 times, cut off after 30, 15, 15, 20 and 30 seconds, though once the cycle is asked to stop, a read of a page of bans makes no more attempts, and stops waiting, for the budget, a pause, `Retry-After` or another attempt, within a second, so only the attempt already sent can hold it up, for at most 30 seconds. So a cycle that has not reached a safe point 45 seconds after the signal is ended there: the service posts so and prints the cycle's JSON line, as interrupted, with what the phase under way had done by then, its time and, for a step, its counts, for the import with the list it was importing (`inProgress`, see [The JSON line](#the-json-line)), and in at most 5 more seconds it saves the cycle's record, shows that it stopped in its status message, with the cycle as the last one, saves how it ended and sends its log messages. It then stops the statements the cycle still has running on the database, closes the locks' connection, which frees them, and exits 0, all within 55 seconds of the signal. A cycle that reaches its safe point meanwhile cuts none of it short, and adds nothing to it. The cycle's step goes on until the service exits, and what it does in those seconds is in no record. A statement it still has running, e.g. one that waits for a row lock, is stopped before the locks are freed, as MySQL would otherwise carry it out, also once another importer holds them: the locks' connection closes the service's other database connections on MySQL's side, with `KILL`, which ends their statements and rolls back what they had not committed. MySQL lets a connection do that to the connections of its own user, and all of the service's use `DATABASE_URI`'s. A BattleMetrics request still waiting for its answer is cut off, as by docker stop's kill: an export ban claimed for it stays claimed, and the next run looks for its ban before it makes it again. The next cycle carries on with the work. A second signal ends the service at once, closing the locks' connection, which frees them. It exits 3 if a cycle was under way, as that cycle's JSON line is printed but not saved, and otherwise with the code the service was already stopping with, 0 or 1.
- **The locks.** A service that loses its locks, e.g. as MySQL restarted and closed their connection, stops the cycle under way at its next safe point and exits 1, for Docker to start it again, as another run may have taken them meanwhile. A manual run started while the service runs, e.g. with the script, is skipped, with exit code 75, as any other start is, also between cycles. To run the importer by hand, stop the service first (see step 5 below).
- **Waiting for the run lock.** A cycle that finds the run lock held, as a run of an importer from before the service lock may hold it, e.g. one started by hand with an older image, waits for that run to end, trying again every 15 seconds, and posts once that it waits. Its time limit starts once it holds the run lock. While it waits, its status message, which the service's first cycle posts then, before its migrations, and the health check say so, and the service checks once a cadence whether the importer is stale. A run of an older importer that was cut off from MySQL holds the run lock for as long as MySQL keeps its connection, up to 8 hours: to see which connection holds it, how long it has been idle, and free it, see [The locks](#the-locks).
- **Standing by.** While another run holds the service lock when the service starts, e.g. the script's last run, or the database cannot be reached to take it, the service stands by, trying again every 15 seconds, and says so in the console. While another run holds the lock, it checks once a cadence whether the importer is stale, as a skipped start does. It posts nothing else until it holds the lock. A process that was cut off from the database without closing its connection, e.g. by a network partition, holds its locks on MySQL until MySQL closes that connection, within 5 minutes, so a service that Docker starts again meanwhile stands by for up to 5 minutes; to free them at once, see [The locks](#the-locks).
- **The database.** A cycle that finds the database unavailable as it starts waits for it, trying again after 5, 10, 20 and 40 seconds and then every minute, for as long as it takes, and its record shows how long it waited. The locks' connection, though, is used every minute, and fails once MySQL has not answered it for 30 seconds, so an outage at any time that lasts more than 30 seconds can end the service as a lost lock does, with exit code 1, and one of more than 90 seconds always does, as does a restart of MySQL, which closes the connection at once. Docker then starts it again, and the new process stands by until the database answers and it takes the service lock. Only a shorter outage is waited out without exiting.
- **Failures.** A cycle that fails, e.g. as a step or a migration failed, is posted as a run's failure is, and the next cycle starts as usual. A promise that fails with nothing to handle it fails the cycle it failed in, not the cycles after it.

| Code | Meaning                                                                                                                                                                                                                                    |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `0`  | The service stopped, as it was asked to with `SIGTERM` or `SIGINT`, also when a second signal came between cycles or while it was ending, or its cycle was ended 45 seconds after the signal.                                              |
| `1`  | It lost its locks, a cycle did not stop within 60 seconds of its time limit, or it failed, also when a second signal came while it was ending for one of these. Docker starts it again, unless `docker stop` or a stack update stopped it. |
| `3`  | A second signal ended it at once, during a cycle.                                                                                                                                                                                          |

### Health

The service answers on `127.0.0.1:3001` inside its container, and `ban-importer/healthcheck.js` asks it, for the health check that the compose service defines below. Runs in once mode start no server, and the image itself defines no health check, so the script's runs are unaffected. The service is healthy:

- while it holds the service lock and a cycle ended, however it ended, within two cycles and the time limit, 35 minutes at the defaults, or, before its first cycle has ended, it took the lock within that time;
- while it waits, for its first 10 minutes of waiting: for the database, or for another run to end, as another run holds the run lock as a cycle starts, or the service lock before the service holds it;
- and not once it is stopping.

Whether its cycles succeed is for the stale alert to say. Docker shows the health check's last answers, each the service's status as JSON, with why it is healthy or not, the last cycle, what it waits for, if anything (`waitingFor`: `database` or `lock`), what it posts to Discord (`discord`: its `IMPORTER_LOOP_DISCORD`, or `off` when it posts nothing at all, as without `DISCORD_LOG_WEBHOOK`), and the process's memory:

```bash
docker inspect --format '{{json .State.Health}}' cbl-importer | jq '.Log[-1].Output | fromjson'
```

### The log channel in loop mode

Alerts are posted as runs post them, in every mode: failures, held removals, lost access, staleness, and the service's own lines, such as a signal, a lost lock or a cycle's time limit. Warnings about invalid settings, and that a dry run is on, are posted once, by the first cycle that runs the step they are about, and printed in the console by the later ones, as every cycle has the same settings. What else the service posts, `IMPORTER_LOOP_DISCORD` says:

- **`changes`**: the embed of each cycle that changed something or had a problem, posted once the cycle has ended, drawn as a run's embed is, and titled with the cycle's number, e.g. `CBL update cycle 12 finished`. A cycle changed something when it added, updated or removed bans, which includes a SteamID move it applied, as that updates the ban, marked bans expired, created or deleted export bans, or its reputation check queued players whose points did not match their bans. It had a problem when it failed or was stopped, a list failed, a list read in full held bans that it no longer has, or it posted a line to the log channel, such as a warning or an alert. A quiet cycle, which polled the lists and found nothing new, posts nothing at all. Refreshing Steam profiles and recalculating players are not changes, nor are SteamID moves that are only counted, nor a reputation check that found every player's points matching.
- **`status`**: one status message for the service, edited at most once a minute, while anything it shows changes, and once more, at once, when the service stops: when the service took the service lock, the cycle under way, with its step and how far the step has got, or what it waits for, the database or another run to end, or when the next cycle starts, the last cycle's outcome, duration and changes, and the totals since the last hourly summary, with the players the reputation check queued, when it queued any. Times are Discord timestamps, which each viewer sees in their own time zone and which stay current between edits. When the service stops or fails, its last edit says so, and why. The message's ID is kept in `ImporterState` (`importerService`), so after a restart the service edits the same message, or posts it again below newer ones as it keeps it at the bottom of the channel (see below), and posts a new one if it was deleted, as it does when it finds it deleted while it runs. On each whole hour, the first at least half an hour after the service took the service lock, it posts an hourly summary: the cycles run, failed and stopped, the bans added, updated, removed and expired, the export bans created and deleted, the players the reputation check queued, when it queued any, the BattleMetrics requests the service sent, retries included, the Steam profiles updated and the slowest cycle.
- **`both`**, the default: both of these.

`importerService` also says when the process that keeps the message up to date started, and whether it said how it ended. A process that ended without saying so, e.g. as it was killed, ran out of memory, was ended at once by a second signal, or could not reach the database as it ended, is posted about by the next one. When the service's final edit finds the message deleted, and posts it again, the service saves the new message's ID with how it ended, once that edit has been sent, so the next process edits the message that says how this one ended. The end waits for that edit for as long as its time allows, keeping 5 seconds to save the ID, so only an edit that Discord holds up for longer, e.g. for more than half a minute of rate limits, leaves the deleted message's ID, and the next process posts the message once more. The service also corrects the status message of the last run in once mode, as a run does, if it still says that run is in progress.

Without `DISCORD_LOG_WEBHOOK`, or with one that is not a Discord webhook, the service posts nothing at all, not even alerts. It says so in the console when it starts, and the health check gives `"discord": "off"`. The compose service below makes a stack update without `DISCORD_LOG_WEBHOOK` fail instead.

Nothing the service posts waits for Discord, and its messages go through the same queue, with the same limits, as a run's, which the web server and the bot share the webhook with. The status message is edited at most once a minute while a cycle goes, and not between cycles, so at a cycle of 10 minutes, a cycle that only polls edits it about twice, and one that reads every list in full up to about 10 times. Each cycle that changed something adds one post in `changes` and `both` mode, and each hour the summary one more. During an outage of BattleMetrics, every cycle fails its lists, so each posts a line for each list that fails, and its embed, and from 3 cycles on, the stale alert once a cadence: at a cycle of 10 minutes, about 20 lines and an embed every 10 minutes. Keeping the status message at the bottom (below) adds a post and a delete each time it moves, at most once a minute, and once more after each embed and summary of the service's own, and, while Discord fails such a delete, a change of the old copy and up to three tries more of both in the minute after.

### The status message at the bottom

With `IMPORTER_STATUS_AT_BOTTOM=1`, the default, the service keeps its status message below the other messages that CBL's services post to the log channel, in `status` and `both` mode, so what the service is doing now is at the bottom of the channel, within the limits below, rather than drifting up the channel as cycles' embeds, hourly summaries, alerts and the web server's and the bot's lines are posted below it. When a newer message is there, the service posts its status message again, as a new message, below it, saves the new message's ID in `importerService` at once, and only then deletes the old one, so there is never a moment without a status message. It finds the newer messages in two ways:

- **Its own**: every message the service posts, which it knows of as soon as Discord has posted it. Its own embed of a cycle, and its hourly summary, are followed within seconds: 3 seconds after Discord posted it, which lets the lines posted with it go first.
- **The web server's, the bot's, and an earlier process's**: each service writes the ID of the newest message it posts to the database, in `ImporterState` (`lastLogMessage`), which keeps only the newest of all, and the importer service reads it once a minute, from its last check or move on. Their lines are followed within about a minute. Each service writes in the background, once Discord has posted the message, at most once every 5 seconds and one write at a time, so it never holds up or fails a request, a command or a line, and never uses more than one database connection for it. A write that fails, e.g. as the database is down, is tried again a minute later, with the newest message by then, and the console says so once. A write that the database never answers is not warned about, and that service writes nothing more until it ends.

Apart from after its own embeds and summaries, the status message moves at most once a minute. The service's end never moves it: its final edit, which says the service stopped or failed, is made where the message is, so the line that says the service is stopping stays below it. After a restart, the next process posts the status message again at once, below that line, and deletes the old one, unless `lastLogMessage` says the saved message is still the newest, e.g. as Discord did not post the line, when it edits it where it is. When the database has no newest message yet, or cannot be read, it posts it again too. A process that ended without saying how, e.g. as it was killed, posted no such line, but the next one posts a line about it, below the saved message, so it always posts the status message again then.

Each move is a new message in the channel, which moves the channel's unread marker, and a delete. When the delete fails, e.g. while Discord is failing, the old copy is changed to say that the status moved to the bottom of the channel, so it no longer looks like the current one, and the delete is tried again with the next check or move. When Discord fails that change too, the old copy still shows the status as it was when it moved, so both are tried again 5, 15 and 30 seconds later, and then with each check, until one works, and meanwhile the status message is not moved again, so a longer failure leaves one such copy rather than one more with each move. A copy that Discord refuses to delete, with a 4xx other than 429, which it would give again, is only changed, and left once it is, or as it is once Discord refuses that too. The old copies still to be deleted or changed are kept in `importerService`, so the next process tries those this one could not. The console says which message was posted in place of which, and which old copy was deleted or left; message IDs are not secrets, unlike the webhook's address, which is never printed.

What it cannot promise: the status message is the last of CBL's messages, and the only one that shows the service as running, but for these cases.

- While Discord fails both the delete and the change of an old copy, until one of them works, as above, or for good once Discord refuses both.
- When Discord posts a move but does not answer within 30 seconds, the service never learns the new message's ID, so it keeps editing the old one, and the new one stays as it was then, until someone deletes it. So it does when a process is killed between a move's post and the save of the new ID.
- Lines that were waiting to be sent when the status message moved are posted below it, as a status message goes ahead of lines, so they stay below it until the next check moves it again, a minute later at most. Lines that another service could not write to the database (below) stay below it longer.

Such a copy keeps the times it showed, e.g. `Next cycle 3 hours ago`, which Discord shows relative to now, so it soon reads as stale.

What it cannot see: messages that people post in the channel themselves, and messages other webhooks or bots post there, as only CBL's own services write their newest message to the database. Below such a message, the status message stays where it is until a CBL service posts again. Nor can it see a message that a service posted while its writes failed, e.g. as the database was down, until that service's next write, a minute after the failure, and the importer service's next check after that. As the service ends, it gives the lines still waiting to be sent, such as the one that says it is stopping, which its final edit goes ahead of, up to 2 seconds, writes the newest message it has posted, and then nothing more, as it closes its database connections. A run that finished writes its newest message before it closes them too. Lines sent after that, e.g. a stopped cycle's last lines, are not written.

With `IMPORTER_STATUS_AT_BOTTOM=0`, the status message is edited where it is, as before, after a restart too, and the service reads nothing from the database for it, though old copies left by an earlier process are still deleted. The web server, the bot and the importer still write their newest message.

### Memory

Nothing grows from one cycle to the next: each cycle has a record of its own, and the import's, the export push's and the steps' own counts are made afresh each cycle. What the export push remembers about owners' webhooks, which webhooks Discord said are deleted and which lists have one that is not a Discord webhook, lasts one cycle, as it lasted one run, so a list whose webhook is not a Discord webhook is posted about once in each cycle that has an alert for it. The service's own state, its signal handlers, its timers, its waits and its status message, is made once, and its totals since the last hourly summary start afresh each hour. Each cycle's JSON line and the health check give the process's memory, to watch over days. `NODE_OPTIONS=--max-old-space-size=768` keeps Node's heap below `mem_limit: 1g`, so a process that ever needed more would fail with an out-of-memory error of Node's own, which Docker restarts and the next process posts about, rather than be killed outright.

### Moving from the script to the service

The service in the Portainer stack, to paste under `services:`. It runs the image of one commit, given in the stack's environment as `IMPORTER_TAG`, e.g. `IMPORTER_TAG=sha-1a2b3c4`, so CI's pushes of `latest` never change it, and the Portainer webhook, which updates the stack after each push, leaves it running as it is. Without `IMPORTER_TAG`, the stack update fails, saying so, rather than run an image nobody chose. The other variables are the stack's, passed by name as the web service has them, and a stack update without any of those the importer needs fails in the same way, rather than start a service that posts nothing, not even alerts, as it would without `DISCORD_LOG_WEBHOOK`, or links owners' alerts to `http://localhost`, as it would without `HOST`. So check that the stack's environment has each of them, as the script's env file does. `BATTLEMETRICS_ORGANIZATION` may be left out, as the importer, like the web server and the bot, then uses CBL's organisation, 56746.

```yaml
importer:
  # The importer image of one commit, set in the stack's environment, e.g. IMPORTER_TAG=sha-1a2b3c4.
  image: werewolfboy13/cblimporter:${IMPORTER_TAG:?set IMPORTER_TAG to the sha- tag of the importer image to run}
  container_name: cbl-importer
  depends_on:
    db:
      condition: service_healthy
  environment:
    # A stack update without any of these fails, saying which.
    DATABASE_URI: ${DATABASE_URI:?set DATABASE_URI in the stack environment}
    BATTLEMETRICS_API_KEY: ${BATTLEMETRICS_API_KEY:?set BATTLEMETRICS_API_KEY in the stack environment}
    STEAM_API_KEY: ${STEAM_API_KEY:?set STEAM_API_KEY in the stack environment}
    DISCORD_LOG_WEBHOOK: ${DISCORD_LOG_WEBHOOK:?set DISCORD_LOG_WEBHOOK, or the importer service posts no alerts}
    HOST: ${HOST:?set HOST to the website address, which owners' alerts link to}
    # Without it, the importer uses CBL's organisation, 56746.
    BATTLEMETRICS_ORGANIZATION: ${BATTLEMETRICS_ORGANIZATION:-}
    NODE_OPTIONS: --max-old-space-size=768
    IMPORTER_MODE: loop
    IMPORTER_CYCLE_SECONDS: '600'
    IMPORTER_MAX_CYCLE_SECONDS: '900'
    IMPORTER_LOOP_DISCORD: both
    # The importer's own BattleMetrics budget, in the correct spelling. The script's env file may
    # still have the old BATTLEMETRICS_API_RESERVIOR, which is not needed here.
    BATTLEMETRICS_API_RESERVOIR: '120'
  init: true
  stop_grace_period: 60s
  healthcheck:
    test: ['CMD', 'node', '/opt/workdir/ban-importer/healthcheck.js']
    interval: 30s
    timeout: 10s
    retries: 3
    start_period: 120s
  networks:
    - backend
    - frontend
  restart: unless-stopped
  mem_limit: 1g
  read_only: true
  cap_drop:
    - ALL
  # The service's log is kept until its container is removed, so it needs a size limit.
  logging:
    driver: json-file
    options:
      max-size: '50m'
      max-file: '5'
```

- **Networks.** In the stack file, the networks are named as the stack declares them, `backend` and `frontend`, which Docker names `cbl_backend` and `cbl_frontend` for the stack `cbl`, the networks the script's `docker run` attaches.
- **Logging.** The service keeps running, so its log is never removed with its container, as a run's is, and it needs the size limit its `logging:` gives. Until the export recalculation only recalculates the players whose bans changed, every cycle prints about 7 lines for every 250 players, even one that only polls: at production size, about 145,000 players, about 4,300 lines, or 0.4 MB, a cycle, and about 55 MB a day at a cycle of 10 minutes. A cycle that reads lists in full prints about 3 more lines for each page of bans it reads. `driver: json-file` with `max-size: '50m'` and `max-file: '5'` keeps about 4 days of cycles at 10 minutes, and less at shorter cycles; `max-size: '10m'` keeps less than a day. A stack file whose services share their logging settings in an `x-logging: &logging` block, with such a limit, can give this service `logging: *logging` instead, but only then: without that block, `*logging` makes the whole stack file invalid, and Portainer refuses every update of the stack, the CI webhook's included, until it is fixed. The cycles' JSON lines are the lines worth keeping, and `ImporterState` keeps the records of the latest 100 cycles too.
- **The database's health.** `condition: service_healthy` needs the `db` service to have a health check; if it has none, use `condition: service_started`, as the service waits for the database itself.
- **Other settings.** Add any of the importer's own settings that the script's env file sets, e.g. `IMPORTER_SCAN_COUNT_CHECK_SKIP` or `IMPORTER_BM_SEARCH_LOOKUP`, but not `IMPORTER_CADENCE_SECONDS` or `IMPORTER_MAX_RUN_SECONDS`: a cadence of an hour, left from the hourly script, would make the service stale only after 3 hours, and give each cycle an hour's worth of Steam profiles. The full reads go by `IMPORTER_CYCLE_SECONDS` whatever it says. To list the file's variables without their values: `cut -d= -f1 .envimporter`.

To move from the script to the service:

1. Merge, and wait for CI to push `werewolfboy13/cblimporter:sha-<commit>`.
2. Stop the script's schedule, so it starts no more runs, and let a run that is under way end: `docker wait cblimporter` waits for it.
3. Add `IMPORTER_TAG=sha-<commit>` to the stack's environment, paste the service under `services:`, and update the stack. The service waits for the database, takes the service lock, standing by while a run still holds it, and starts its first cycle.
4. Check the first cycles: their JSON lines (above), the health check, which turns healthy at its first check, 30 seconds after the start, and the status message in the log channel. The first cycle may read every list in full, which takes about 9 minutes in production.
5. Keep the script for runs by hand: a run it starts while the service runs, also between cycles, is skipped, with exit code 75. To run it by hand, stop the service with `docker stop cbl-importer`, run the script, and start the service again with `docker start cbl-importer`. Do it while nothing is being merged: an update of the stack, which the CI webhook makes after every push to master, starts the stopped service again, and a run the script starts after that is skipped. A run already under way holds the locks, so the service then stands by until the run ends.

The bot needs no change for the service: it refuses the changes that must not overlap a run while the run lock is held, as it always has, and the service holds the run lock only during its cycles.

To go back to the script, remove the `importer` service from the stack and update the stack, which stops and removes its container and frees the locks, and then re-enable the script's schedule, whose next run takes them. Stopping the container instead, with `docker stop` or Portainer's Stop button, lasts only until the next update of the stack, which starts it again, and the CI webhook updates the stack after every push to master: the service then holds the service lock again, and every run the script starts is skipped, with exit code 75.

`IMPORTER_TAG` can go back only to an image that has the importer service, from the commit that added it on. An older image has no loop mode or health check: it runs once and exits, and `restart: unless-stopped` starts it again at once, so it would run back to back, each run posting its own status message and refreshing the Steam profiles of a 6-hour cadence. To go back to an importer from before the service, go back to the script, as above, and have the script run that image.

### Changing its settings

Change a setting in the service's environment, in the stack editor, and update the stack. Docker then stops the service, which stops at its next safe point, and starts a new one with the setting, which edits the same status message.

- **`IMPORTER_LOOP_DISCORD`**: `changes`, `status` or `both`, as above, at any time. Going to `changes` leaves the status message as it was last edited, saying the service stopped, until the service goes back to `status` or `both`, when it edits the message again.
- **`IMPORTER_STATUS_AT_BOTTOM`**: `1` or `0`, as above, at any time. Going to `0` leaves the status message where it is, and edits it there from then on; going back to `1` moves it to the bottom again, at the restart.
- **`IMPORTER_CYCLE_SECONDS`**: start at `600`. Once the export recalculation only recalculates the players whose bans changed, and after a clean day, go to `120`, then `60`. The lists keep their slots, so their full reads stay spread over the new cycles. Keep `IMPORTER_MAX_CYCLE_SECONDS` longer than the longest cycle, one that reads every list in full, about 9 minutes in production, and the health check's window, two cycles and the time limit, follows both.
- **`IMPORTER_TAG`**: set it to the `sha-` tag of each importer change that is merged, to run it. Setting it back to an earlier tag goes back to that commit, as long as its image has the importer service (see above).
